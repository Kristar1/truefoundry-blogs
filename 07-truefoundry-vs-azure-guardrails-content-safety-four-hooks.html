Guardrails & the Four-Hook Model: TrueFoundry vs Azure

What this blog argues

Most safety-policy comparisons walk content categories. Hate, sexual, violence, self-harm — the "what" of harmful content. The "what" matters, but for AI systems that use tools, the more consequential question is the where. How many points in the request flow can a guardrail intercept? An AI agent that calls tools has a request lifecycle with at least four enforcement points: the user's prompt before it reaches the LLM (LLM Input), the LLM's text response before it reaches the user (LLM Output), the LLM's tool call before it reaches the tool (MCP Pre-Tool), and the tool's response before it reaches the LLM's next turn (MCP Post-Tool). APIM's llm-content-safety policy covers two — input and output — using Azure AI Content Safety. TrueFoundry's guardrail engine covers all four hooks as first-class primitives, with two execution modes (Validate runs guardrails in parallel with cancel-on-fail; Mutate runs them sequentially by priority for content modification) and three failure-handling strategies (Enforce, Enforce-But-Ignore-On-Error, Audit). For text-only LLM workloads the gap is small. For tool-using agents the gap is decisive — and tool-using agents are increasingly the workloads that matter.

§0 — TL;DR & Quick-Picks

A guardrail incident that becomes a hook-coverage question

An IT-support team at a 12,000-person enterprise rolls out an internal AI assistant in late February. The assistant has access to four tools through MCP: read_ticket, create_ticket, read_kb_article, and — gated behind a feature flag for the team's tier-2 support engineers — read_employee_record. The architecture is competent. Input guardrails through Azure AI Content Safety check user prompts for jailbreak attempts and harmful content; output guardrails check LLM responses before they reach the user; the four content-safety categories are configured at threshold 4. Pen-testing before launch found no exploitable injection paths through prompts or completions. Production rolls out at the end of the month.

Three weeks later, an internal red-team exercise finds something the pre-launch pen-test missed. The exploit path: a tier-2 engineer (who legitimately has the read_employee_record tool) is socially engineered into pasting an attacker-supplied document into the assistant. The document contains a benign-looking instruction sentence in a context the engineer doesn't realize is adversarial. The LLM, processing the document content, generates a tool call: read_employee_record(employee_id="12345") — for an employee whose record the engineer has no business reason to read. The input guardrail saw the user's prompt: pasting the document. Threshold-4 content categories cleared it. Prompt Shields saw an indirect-injection attempt but rated it below the block threshold. The output guardrail saw the LLM's response: a confirmation message saying the lookup was performed. Threshold-4 content categories cleared that too. Neither guardrail saw the tool call itself — the structured invocation that, in the request lifecycle, sits between the LLM's reasoning step and the actual tool execution.

The red-team's writeup is precise. The architectural gap is not in the content categories — those did exactly what they were configured to do. The gap is in the hook coverage: input and output are inspected; the tool boundary is not. A guardrail running at the MCP Pre-Tool hook would have inspected the tool call's parameters before execution, applied a parameter-validation policy (employee_id reads must match employee_id from the authenticated user's reporting chain), and either blocked the tool call or routed it to a human reviewer. A guardrail running at the MCP Post-Tool hook would have inspected the tool's response before it returned to the LLM's next turn, applied a sensitive-data policy, and prevented secrets from making the round-trip back into the next prompt. Neither hook exists in the deployed architecture.

The remediation is two months of work. The team builds custom MCP middleware that inspects tool calls before they reach the MCP server and tool responses before they return to the model. They add a parameter-validation step keyed to employee directory data. They add an audit log for every tool invocation with the full call+response captured. They add human-in-the-loop review for sensitive tool calls with privilege escalation. The fix works, but the team has built — at considerable cost — what their AI gateway should have provided as a first-class primitive. The architectural lesson is one this blog is about: guardrail comparisons that walk content categories miss the hook-coverage question, and for tool-using agents the hook-coverage question is the one that decides safety.

TL;DR
  • Azure: llm-content-safety covers two hooks — input + output. Backed by Azure AI Content Safety with Hate / SelfHarm / Sexual / Violence categories and configurable severity thresholds (0–7, lower = stricter). Prompt Shields adds jailbreak detection on input. Groundedness Detection adds RAG-grounding evaluation on output. Protected Material and Custom Categories are first-class. The MCP-tool boundary is not a first-class hook. Task Adherence (the newest Content Safety feature) is the closest equivalent for tool-call inspection but operates at a different architectural layer.
  • TrueFoundry: four hooks as first-class primitives. LLM Input, LLM Output, MCP Pre-Tool, MCP Post-Tool. Each hook is a configurable checkpoint that can attach guardrails. Two execution modes: Validate (guardrails run in parallel; if any fails, the request is canceled — fast for safety checks) and Mutate (guardrails run sequentially by priority order; each can modify the payload — for content rewriting). Three strategies: Enforce (block on any failure), Enforce-But-Ignore-On-Error (block on policy violation, allow on infrastructure error), Audit (never block; emit observability data only).
  • Streaming behavior matters and both products handle it. APIM's stream handler buffers events in a sliding window and stops forwarding when a violation is detected (no 403 — the stream just terminates). TrueFoundry's hook engine has equivalent streaming semantics for output guardrails.
  • Honest framing. For text-only chatbot workloads, APIM's two-hook coverage is sufficient and the Azure AI Content Safety integration is genuinely best-in-class — the model quality, the language coverage, the Prompt Shields and Groundedness Detection, the deep integration with Foundry. For tool-using agent workloads, the four-hook architecture is structurally better-fit because the tool boundary is where privilege escalation happens.
Quick-Pick
Azure
The right call when the workload is text-only LLM (no tool use), when Azure AI Content Safety's category coverage and language support are required, when Prompt Shields and Groundedness Detection are mission-critical, or when the team has institutional muscle around Azure AI Content Safety as the safety surface across multiple workloads.

§1 — The hook-coverage question

Guardrail comparisons that walk content categories find feature parity quickly. Hate, sexual, violence, self-harm — both products cover the four standard categories. Both have jailbreak detection. Both support custom blocklists. Both handle streaming. The category-coverage comparison is correct but skips the architectural question that decides whether the guardrails actually catch the incidents the team is trying to prevent.

The architectural question is where: at how many points in the request lifecycle can a guardrail intercept and act? For a text-only chatbot, two points are sufficient — the user's prompt before the LLM sees it (input), and the LLM's response before the user sees it (output). For a tool-using agent, two points are not enough; the tool boundary is a third and fourth point that need their own enforcement, because tool calls are where structured privilege escalation happens and tool responses are where sensitive data leaves the trust boundary.

The four hooks of an agentic request lifecycle

Walking the lifecycle of an agentic request explicitly:

  1. LLM Input hook. The user's prompt arrives at the gateway. Before the gateway forwards to the LLM, the input hook can inspect: prompt content (harmful categories, blocklist matches), prompt structure (jailbreak patterns, indirect injection in attached documents), and metadata (caller identity, request class). Both products implement this hook.
  2. LLM Output hook. The LLM's response arrives at the gateway. Before the gateway returns to the user, the output hook can inspect: response content (harmful categories), response structure (PII leakage, protected material), and grounding (whether RAG-context was correctly used). Both products implement this hook.
  3. MCP Pre-Tool hook. The LLM has decided to call a tool. The gateway has parsed the structured tool call from the LLM response. Before the gateway forwards the call to the MCP server, the pre-tool hook can inspect: tool name (allowed tools for this caller), parameters (parameter-validation policies, sensitive-value detection), and reasoning (why is the LLM calling this tool with these args). This hook is the architectural piece that the IT-support red-team scenario at the top required.
  4. MCP Post-Tool hook. The tool has returned a response to the gateway. Before the gateway returns the response into the LLM's next-turn context, the post-tool hook can inspect: tool response content (sensitive data leakage), response structure (PII, secrets, internal identifiers), and consistency (does the response match what the call requested). This hook is what prevents secret-leakage from tool responses round-tripping back into prompts.

Why hooks 3 and 4 matter even when hooks 1 and 2 are well-configured

The IT-support scenario at the top of this blog is precisely the failure mode of a two-hook architecture trying to protect a four-hook lifecycle. Input was inspected; the document was not classified as harmful. Output was inspected; the response did not contain harmful content. Neither inspection saw the tool call — and the tool call was where the privilege escalation happened. This is not a failure of the categories; threshold-4 was correct. It is not a failure of Prompt Shields; it caught the indirect-injection attempt but rated it below block-threshold (correctly — it was a benign-looking instruction). The failure is structural: the architecture didn't have a hook at the place where the harmful action occurred.

For an agentic system the rule of thumb is: the most security-relevant hooks are pre-tool and post-tool, not input and output. Input and output guardrails catch obviously harmful content. Pre-tool and post-tool guardrails catch privilege escalation, parameter-injection, and sensitive-data exfiltration — the classes of attack that are increasingly dominant as AI workloads move from chat to action.

The honest boundary on this argument

Azure has a credible answer to part of this gap: Azure AI Content Safety's newer Task Adherence feature inspects LLM behavior to detect misaligned tool invocations and inconsistencies between responses and user intent, and it can block misaligned actions or escalate to human review. This is real and worth naming — Microsoft is clearly aware of the agentic safety question and is building toward it. The architectural fact that this blog is about, however, is that Task Adherence is a Content Safety feature consumed by applications, not an APIM gateway-policy hook. A team using AOAI directly with Foundry's content filter can configure Task Adherence; a team using APIM as the policy boundary doesn't have a corresponding gateway-policy primitive to enforce tool-boundary inspection. The four-hook model is the architectural shape that integrates this kind of inspection at the gateway-policy layer rather than at the application-orchestration layer. Different layer; different fit.

The rest of the blog walks both architectures in working detail. §2 walks the Azure guardrail surface — llm-content-safety with Azure AI Content Safety, the four standard categories, severity levels, Prompt Shields, Groundedness Detection, Protected Material, and the streaming-buffer behavior — with a working policy composition. §3 walks TrueFoundry's four-hook model with the Validate vs Mutate modes and the three strategies — with a working configuration that demonstrates each. §4 walks three guardrail scenarios side-by-side. §5 ends with the editorial verdict.

Microsoft§2 — Azure: llm-content-safety + Azure AI Content Safety

APIM's content-safety surface is the gateway-policy front-end for Azure AI Content Safety, Microsoft's standalone safety service. The architectural choice is clean: APIM doesn't reimplement category detection — it routes content to Azure AI Content Safety, applies the policy decision, and either blocks or forwards. Azure AI Content Safety is itself a mature, well-engineered service with category models trained on 8 languages plus working coverage in many more; for what it does, it is genuinely best-in-class.

Layer 1 — The two hooks: input and output

The llm-content-safety policy is configured in two places in the policy XML:

  • Inbound section — checks user prompts before they reach the LLM. This is the LLM Input hook. With shield-prompt="true", Prompt Shields is enabled to detect jailbreak attempts and indirect injections.
  • Outbound section — checks model completions before they return to the user. This is the LLM Output hook. Alternatively, enforce-on-completions="true" on the inbound configuration extends the inbound check to cover responses as well.

The two-hook coverage matches the two-step request/response lifecycle of a text-only LLM. There is no third or fourth hook in the policy structure. For workloads that don't use tools, this is exactly right; for workloads that do, the gap is where the architectural argument sits.

Layer 2 — Categories, severity levels, and the threshold convention

The four standard harm categories are Hate, SelfHarm, Sexual, and Violence. Each is configured with a numeric threshold:

  • FourSeverityLevels: output severities in four buckets — 0, 2, 4, 6.
  • EightSeverityLevels: output severities at full granularity — 0 through 7.
  • Threshold convention: "The value must be between 0 (most restrictive) and 7 (least restrictive)" per Microsoft's policy reference. Content with severity below the threshold passes; content at or above the threshold blocks. A threshold of 4 with FourSeverityLevels blocks content at level 4 or 6 and allows 0 or 2.

The threshold convention is important to internalize: raising the threshold raises tolerance (fewer blocks, more content gets through); lowering the threshold raises strictness (more blocks). Most teams new to this confuse it on first deployment.

Layer 3 — Prompt Shields, Groundedness Detection, and Protected Material

Three additional capabilities compose with the category model:

  • Prompt Shields — detects jailbreak attempts (User Prompt attacks) and indirect injection attempts (Document Attacks where adversarial content is embedded in a document the user has provided). Activated via shield-prompt="true". This is the layer that catches "ignore your previous instructions" and similar adversarial patterns.
  • Groundedness Detection — for RAG workloads, evaluates whether the LLM's response is actually supported by the retrieved context. Detects hallucination at the response layer. Available in Central US, East US, France Central, and Canada East.
  • Protected Material — detects copyrighted text (song lyrics, articles) and copyrighted code (against a public-GitHub-repo index, with the documented caveat that the code index is current through April 2023). Useful for chatbot products that must avoid reproducing licensed content.

For text-only workloads, the combination is comprehensive. A chatbot with input categories at threshold 4, Prompt Shields enabled, output categories at threshold 4, Groundedness Detection on RAG responses, and Protected Material checks on completions has a defense-in-depth posture that matches anything available in the industry — for the workload shape it targets.

Layer 4 — Streaming behavior and the no-403 termination

One operationally important detail: for streaming responses, the policy reference says "the stream handler buffers events in a sliding window and, if a content safety violation is detected, stops forwarding further events to the client. A 403 error isn't returned in this case." The stream just terminates. Clients consuming streamed responses must handle truncation as a possible safety-block signal — there's no exception code to dispatch on. This is a sensible engineering trade-off (you can't return a 403 mid-stream after data has already been sent), but it shapes how clients code against the streaming API.

Layer 5 — Capacity, language, and length constraints

A few constraints that affect production accuracy:

  • Maximum input length: 10,000 characters per Content Safety request. Longer content must be chunked at word boundaries and inspected per chunk; if any chunk fails, the whole content is blocked.
  • Minimum scan length: 110 characters for LLM completions (Groundedness Detection). Below this, the scan doesn't run.
  • Language coverage: Native training in Chinese, English, French, German, Spanish, Italian, Japanese, Portuguese; working in many other languages with quality variance. Protected Material, Groundedness Detection, and standard Custom Categories work with English only — a real constraint for global workloads.
  • Regional availability for Groundedness Detection: Central US, East US, France Central, Canada East only.

The Azure guardrail topology diagram

Azure guardrail topology — two hooks (input + output) via llm-content-safety backed by Azure AI Content Safety. The tool-call path bypasses the gateway-policy layer; Task Adherence (the closest equivalent for tool oversight) operates at the application layer rather than as a gateway-policy hook.

What the operator writes — text-only chatbot with full guardrail composition

The XML below shows a working composition for a customer-facing chatbot: input check with categories at threshold 4, Prompt Shields enabled, blocklists for brand-specific terms, then the standard token-limit + backend-routing chain, and output check with stricter SelfHarm threshold for the customer-facing context:

        <category name="Sexual" threshold="4" />

    <llm-content-safety backend-id="content-safety-backend">

        <category name="Hate" threshold="4" />
        <category name="SelfHarm" threshold="2" />
        <category name="Sexual" threshold="4" />
        <category name="Violence" threshold="4" />
      </categories>

SelfHarm is set tighter (threshold 2) for customer-facing surfaces; the other three at 4 (the standard "block 4 and above" pattern). Blocklists carry brand-specific terms. The composition is well-engineered for text-only LLM workloads.

What APIM is genuinely strong at — and what the architecture doesn't cover

What APIM's content-safety surface does well is real and worth naming explicitly:

  • Best-in-class category models. Azure AI Content Safety's category quality is mature — the four standard categories are well-trained, the language coverage is broad (8 native languages plus working coverage in many more), and the integration with Foundry is deep.
  • Prompt Shields and Groundedness Detection are operationally valuable. Indirect-injection detection is genuinely hard to get right; Microsoft's implementation is among the best available. RAG groundedness evaluation is decisive for hallucination-sensitive workloads.
  • Streaming-buffer behavior is thoughtful. The sliding-window buffer for streamed responses is the right engineering trade-off — it doesn't block streaming throughput, but it terminates the stream when a violation is detected.
  • The newest features show Microsoft is building toward agentic safety. Task Adherence specifically targets misaligned tool invocations and tool-input/output consistency — the same problem space the four-hook model addresses. The architectural locus is different (Foundry's content filter rather than an APIM gateway-policy hook) but the engineering investment is real.
The honest caveat — the agentic gap at the gateway-policy layer

For text-only LLM workloads, APIM's two-hook coverage is sufficient. For tool-using agents, the gateway-policy layer doesn't have first-class hooks at the tool boundary. Teams operating MCP servers behind APIM today either (1) build custom middleware in front of the MCP server to do parameter validation and response inspection, (2) implement Task Adherence at the application/Foundry layer and accept that the enforcement is application-side rather than gateway-side, or (3) accept the gap and rely on input/output guardrails to catch what they can. Each approach is workable; none is as clean as a gateway-policy hook. For agentic workloads where the tool boundary is the privilege-escalation surface, this is the architectural shape that determines whether the safety review can be conducted at the gateway.

TrueFoundry§3 — TrueFoundry: four hooks, two modes, three strategies

TrueFoundry's guardrail engine is structured as a small, orthogonal set of primitives. Four hook points define where in the request lifecycle a guardrail can attach. Two execution modes define how guardrails behave when multiple are attached to the same hook. Three strategies define what happens when a guardrail fails. The combination produces a configuration matrix that covers the full agentic lifecycle — text and tool — without separate mechanisms for separate cases.

Layer 1 — Four hooks across the request lifecycle

The four hooks correspond directly to the four lifecycle points enumerated in §1:

  • LLM Input. Inspects the prompt before it reaches the LLM. This is the equivalent of APIM's inbound llm-content-safety. Guardrails attached here see the user's prompt, attached documents, system messages, and conversation history.
  • LLM Output. Inspects the LLM's response before it returns to the application. Equivalent to APIM's outbound check. Guardrails attached here see the generated text and any structured outputs.
  • MCP Pre-Tool. Inspects a tool invocation before it reaches the MCP server. Guardrails attached here see the tool name, the parameters the LLM constructed, and the surrounding context. This is the hook that catches privilege escalation through parameter manipulation.
  • MCP Post-Tool. Inspects the tool's response before it returns to the LLM's next-turn context. Guardrails attached here see the tool's full response and can mutate or block it. This is the hook that prevents secrets and sensitive data from round-tripping into the next prompt.

Each hook is a configurable checkpoint. Multiple guardrails can attach to the same hook. The same guardrail type (e.g., a PII detector) can attach to multiple hooks. The configuration is declarative; the engine handles dispatching to the right hook at the right time.

Layer 2 — Two execution modes: Validate and Mutate

Within a hook, multiple guardrails can run. The execution mode defines their concurrency and side-effect semantics:

  • Validate (parallel, cancel-on-fail). All guardrails attached to the hook run in parallel. Each is a yes/no check — does this content pass policy? If any guardrail fails, the in-flight checks are canceled and the request is blocked. Optimized for safety checks where any single failure should block. Latency is min(individual check) for the success case; the slowest check determines the success path's wall time.
  • Mutate (sequential, by priority). Guardrails run sequentially in priority order. Each can modify the payload before the next one runs. The output of guardrail N becomes the input of guardrail N+1. Optimized for content modification — PII redaction, prompt rewriting, response normalization. Latency is the sum of individual checks; ordering matters because earlier guardrails see the original content while later ones see the mutated form.

The Validate-vs-Mutate distinction matters operationally because the two have different design constraints. Safety checks should be parallel and fast-failing because any failure means block; content rewriters need to run sequentially because they layer modifications. APIM's llm-content-safety doesn't expose an analogous distinction — the policy is a single check, and chaining multiple safety policies requires composing them in policy XML with the operator manually managing order and behavior.

Layer 3 — Three strategies: Enforce, Enforce-But-Ignore-On-Error, Audit

The strategy defines what happens when a guardrail check fails or errors out:

  • Enforce. Block on any failure. If the guardrail says fail, the request is blocked. If the guardrail itself errors (the safety service is down, timeout, etc.), the request is also blocked. The right strategy for production safety-critical paths where availability of the guardrail is itself part of the contract.
  • Enforce-But-Ignore-On-Error. Block on policy failure, but allow on infrastructure error. If the guardrail says fail, block. If the guardrail errors out, log the error and let the request through. The right strategy for safety checks that should be applied opportunistically without becoming a single point of failure for availability.
  • Audit. Never block. Run the check, emit observability data, return the request unchanged. The right strategy for new guardrails being evaluated in production traffic before they're enforced — observe the false-positive rate before flipping to Enforce.

The Audit strategy is the operationally important one for rolling out new guardrails safely. A team adding a new content-safety check on a high-traffic endpoint can deploy it in Audit mode for a week, measure the false-positive rate against the actual traffic distribution, tune thresholds based on real data, and then flip to Enforce once the false-positive rate is acceptable. APIM doesn't have a first-class audit-only mode for llm-content-safety; teams achieve similar effect by emitting custom telemetry and accepting the operational cost.

TrueFoundry guardrail topology — four hooks across the agentic lifecycle (LLM Input, LLM Output, MCP Pre-Tool, MCP Post-Tool), with two execution modes (Validate parallel, Mutate sequential) and three strategies (Enforce, Enforce-But-Ignore-On-Error, Audit) defining within-hook semantics.

What the operator writes — agentic config with all four hooks

The YAML below shows a working configuration for the IT-support assistant from the opening scenario, with guardrails attached to all four hooks. Note the per-hook mode/strategy choices: Validate+Enforce for safety checks, Mutate+Enforce for PII redaction at MCP Post-Tool:

YAML
# Illustrative virtual model with full four-hook guardrail config
type: virtual-llm-model
name: it-support-agent-prod
mode: chat-completions

routing:
  - default:
      strategy: latency-aware
      backends:
        - { provider: azure-openai, model: gpt-4o, weight: 100, priority: 1 }

guardrails:
  # HOOK 1 — LLM Input — block harmful content + jailbreak attempts
  - hook: llm_input
    mode: validate            # parallel; any single failure blocks
    strategy: enforce
    checks:
      - { type: content_categories, hate: 4, self_harm: 2, sexual: 4, violence: 4 }
      - { type: jailbreak_detection, threshold: 0.85 }
      - { type: pii_detection, action: block_if_present }

  # HOOK 2 — LLM Output — block harmful completions + check groundedness for RAG
  - hook: llm_output
    mode: validate
    strategy: enforce
    checks:
      - { type: content_categories, hate: 4, self_harm: 2, sexual: 4, violence: 4 }
      - { type: groundedness, source_field: rag_context, threshold: 0.7 }

  # HOOK 3 — MCP Pre-Tool — validate tool params before execution
  - hook: mcp_pre_tool
    mode: validate
    strategy: enforce
    checks:
      - type: tool_allowlist
        allowed_tools_per_role:
          tier1: [read_ticket, create_ticket, read_kb_article]
          tier2: [read_ticket, create_ticket, read_kb_article, read_employee_record]
      - type: parameter_validation
        rules:
          - tool: read_employee_record
            param: employee_id
            rule: must_be_in_reporting_chain_of: ${request.user.id}

  # HOOK 4 — MCP Post-Tool — redact secrets/PII from tool responses
  - hook: mcp_post_tool
    mode: mutate              # sequential; each guardrail can modify payload
    strategy: enforce
    checks:
      - { type: secret_detection, action: redact, priority: 1 }
      - { type: pii_redaction, fields: [ssn, phone, email], priority: 2 }
      - { type: internal_id_redaction, patterns: [employee_id, account_id], priority: 3 }
Composition consistent with TrueFoundry guardrails overview, Guardrail Modes, and Guardrail Strategies. The IT-support agent scenario from §0 is closed by Hook 3 (parameter validation prevents reading employee records outside the user's reporting chain) and Hook 4 (PII redaction prevents secrets from round-tripping into the next prompt).
What this earns operationally

(1) Tool boundary as a first-class enforcement surface. The IT-support red-team scenario from §0 is structurally prevented by Hook 3's parameter validation. (2) One config surface for all four hooks. Adding a new guardrail at any hook is the same shape of change — declarative, in one place, applied through tfy apply. (3) Validate vs Mutate is the right semantic distinction. Safety checks run in parallel and fast-fail; content rewriters run sequentially and layer modifications. The execution model matches the design intent of each guardrail type. (4) Audit strategy makes new-guardrail rollout safe. A team can deploy a new check in Audit mode for a week, measure the false-positive rate against real traffic, and only flip to Enforce once tuning is complete. (5) The architectural primitive matches the workload's lifecycle. For text-only LLMs, hooks 1 and 2 alone work — the architecture doesn't impose tool overhead on workloads that don't use tools. For agentic systems, hooks 3 and 4 are the structural piece that makes the safety review tractable.

§4 — Three guardrail scenarios compared

The three scenarios below walk concrete operational moments where guardrail architecture decides the outcome. Each is shown side by side under both products. The scenarios are realistic patterns from production AI engineering practice.

SCENARIO 1Customer-facing chatbot — text-only, multilingual

A consumer-products company runs a customer-support chatbot in 6 languages (English, Spanish, French, German, Italian, Portuguese). Workload is text-only — no tools, no agentic behavior. Safety requirements: standard four content categories, jailbreak detection, brand-blocklist, hallucination detection on RAG responses.

Azure path

✅ This scenario is exactly what Azure AI Content Safety is designed for. llm-content-safety with all four categories at threshold 4, shield-prompt="true" for jailbreak detection, custom blocklist for brand terms, Groundedness Detection on outbound for RAG-grounded responses (English-only — works for the EN traffic, doesn't apply for the others). The category models work natively in all 6 languages. The team operates one institutional Azure AI Content Safety resource across all chatbot variants. Best-in-class fit. The mature category quality, Prompt Shields, and Groundedness Detection compose into a defense-in-depth posture matching the best in the industry.

TrueFoundry path

Same outcome with Hooks 1 and 2. Hook 1 (LLM Input) with content categories, jailbreak detection, and the brand blocklist. Hook 2 (LLM Output) with categories and groundedness. Hooks 3 and 4 are not configured — this workload doesn't use tools, so the agentic hooks aren't needed. The Validate mode and Enforce strategy are the natural choices for safety-critical chatbot. Equivalent outcome. The two-hook portion of the four-hook model maps directly to this workload; no architectural overhead for the unused hooks.

SCENARIO 2Internal IT-support agent with MCP tools — privilege escalation prevention

The opening scenario closes here. The IT-support assistant has four MCP tools, including a privileged read_employee_record. The architecture must prevent a tier-2 engineer from being socially engineered into reading records outside their reporting chain.

Azure path

Input + output guardrails block obviously harmful content but do not inspect the structured tool call. The team's options: (1) build custom MCP middleware that sits in front of the MCP server and applies parameter validation policies — works but is a custom build the team operates separately; (2) configure Foundry's Task Adherence at the application/Foundry layer to detect misaligned tool invocations — workable but enforcement is application-side rather than gateway-side; (3) accept the gap and rely on input/output guardrails plus directory ACLs on the underlying API — defense-in-depth, but doesn't structurally close the hole. The team in §0 chose option 1 and built two months of custom middleware. Workable; not as clean as a gateway-policy hook at the tool boundary.

TrueFoundry path

Hook 3 (MCP Pre-Tool) is the architectural primitive that prevents this. A parameter-validation guardrail with the rule employee_id must_be_in_reporting_chain_of: ${request.user.id} is enforced at the gateway before the tool call reaches the MCP server. The socially-engineered tool call is blocked at admission. Hook 4 (MCP Post-Tool) provides defense-in-depth — even if a tool call gets through, secrets and PII are redacted from the response before they round-trip into the next prompt. Direct fit; the architecture's strongest scenario. The two months of custom-middleware work the Azure team did is replaced by declarative guardrail config.

SCENARIO 3Rolling out a new PII-redaction guardrail without breaking production

A platform team wants to add a new PII-redaction check on a high-traffic endpoint. The check is well-tested in development, but production traffic includes legitimate uses (e.g., support tickets that contain customer phone numbers as part of the support context) where overzealous redaction would degrade the user experience. The team needs to measure the false-positive rate against real production traffic before flipping to enforcement.

Azure path

APIM doesn't have a first-class audit-only mode for content-safety policies. Workarounds: (1) deploy the new policy as a separate APIM API revision with a small canary percentage, measure block rates, ramp gradually — works but ramping is per-revision rather than per-guardrail; (2) emit the safety check's verdict as a custom dimension on telemetry without acting on it (custom policy expression that calls Content Safety API directly and logs without blocking) — workable but is custom plumbing the team operates; (3) accept the tuning happens in pre-prod and ship to production with the chosen threshold. Each is workable; none has the operational simplicity of a per-guardrail audit flag. Achievable; non-trivial operational effort per new-guardrail rollout.

TrueFoundry path

Add the PII-redaction guardrail to Hook 1 with strategy: audit. The check runs against real production traffic, emits observability data on what it would have blocked, but never blocks. After a week the team reads the observability output, identifies the false-positive patterns (e.g., support tickets where phone numbers are legitimate), tunes the redaction rules to handle those cases, and flips the strategy to enforce. The same guardrail definition; one field changed. Direct fit; the Audit strategy is exactly designed for this rollout pattern.

§5 — Editorial verdict

Best fit
Azure
For text-only LLM workloads, APIM's llm-content-safety backed by Azure AI Content Safety is genuinely best-in-class. The category models are mature with broad language coverage. Prompt Shields catches jailbreak and indirect-injection attacks at quality the industry hasn't matched. Groundedness Detection is the canonical answer for RAG hallucination. Protected Material handles licensed-content concerns. The streaming-buffer behavior is thoughtful. Microsoft's investment in agentic safety (Task Adherence) shows the platform team is aware of the agentic-workload question and is building toward it — at the application/Foundry layer rather than the gateway-policy layer. For organizations with a chatbot-shaped workload and an Azure-anchored stack, this is the right answer.
Choose Azure if: the workload is text-only LLM with no tool use, the team operates Azure AI Content Safety as institutional infrastructure across multiple workloads, the language coverage and category quality of Microsoft's models are mission-critical, or the application-layer Task Adherence enforcement is acceptable for the agentic safety posture.
Best fit
TrueFoundry
The four-hook architecture is the structural fit for tool-using agents. Hook 3 (MCP Pre-Tool) and Hook 4 (MCP Post-Tool) are the architectural primitives that close the gap APIM has at the tool boundary — privilege escalation through parameter manipulation is caught by parameter-validation guardrails before tool execution; sensitive-data leakage through tool responses is caught by Mutate-mode redaction guardrails before next-turn context. The Validate-vs-Mutate distinction matches the design intent of safety checks vs content rewriters. The Audit strategy makes new-guardrail rollout safe against real traffic. For agentic workloads where the tool boundary is the privilege-escalation surface, the architecture's value is real and direct.
Choose TrueFoundry if: the workload uses MCP tools or function-calling agents, the safety review specifically requires gateway-policy hooks at the tool boundary, validate-vs-mutate semantics with explicit failure-handling strategies are operationally important, or rolling out new guardrails against production traffic in audit-only mode is part of the team's safety-engineering practice.

The most honest framing is that the two architectures fit different sides of the AI-workload landscape. Azure's two-hook architecture with Azure AI Content Safety is excellent for the text-only chatbot shape — and for that shape, the integration with Foundry, the language coverage, the Prompt Shields and Groundedness Detection put Microsoft's offering among the best available. TrueFoundry's four-hook architecture is engineered for the agentic shape — and for that shape, hooks at the tool boundary close gaps that the chatbot-architecture leaves at the gateway-policy layer.

The trajectory of AI workloads matters here. Text-only chatbots are the workload of 2023-2024; tool-using agents are increasingly the workload of 2025-2026. Microsoft is clearly aware of this — Task Adherence is real, well-engineered, and operates at the layer Microsoft chose for it. The architectural argument is not that Azure ignores agentic safety; it is that the gateway-policy layer is a different layer, and for teams whose safety review wants gateway-policy enforcement at the tool boundary (rather than application-layer enforcement), the four-hook model fits more cleanly.

For most teams the right answer depends on the dominant workload shape. Chatbot-heavy organizations with Azure-anchored stacks should use APIM's two-hook coverage and Azure AI Content Safety — the integration is excellent. Agent-heavy organizations or organizations whose safety review specifically requires gateway-policy enforcement at the tool boundary should use TrueFoundry's four-hook architecture. Mixed organizations need to evaluate the weighted balance between the two workload shapes.
