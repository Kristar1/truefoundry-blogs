What this blog argues

Observability comparisons that walk feature checklists find parity quickly. Both products produce metrics, logs, and traces; both integrate with industry-standard backends; both support sampling and dashboards. The checklist comparison is correct but skips the architectural question that decides whether AI engineers can actually debug a production incident: what shape are the traces in, and where do they go? The two products optimize for different assumptions. Azure assumes the observability backend is Azure Monitor — Application Insights for traces and KQL queries, Log Analytics for resource logs, Azure Monitor metrics for dashboards, Managed Grafana for visualization. The integration is mature and deep but oriented around Azure-native consumption. TrueFoundry assumes the observability backend is whatever the customer's SRE team already operates — OpenTelemetry-first export with native exporters to Datadog, Honeycomb, Tempo, Grafana Cloud, and any OTLP-compatible collector. The architectural difference is whether AI observability lives in a dedicated Azure-side surface or flows into the customer's existing distributed-tracing stack alongside everything else. For organizations already operating mature OTel pipelines, the second architecture is operationally decisive; for Azure-anchored organizations the first is institutional muscle.

§0 — TL;DR & Quick-Picks

A "weird answer" that becomes a trace-stitching question

Tuesday, 10:14 AM. A senior platform engineer at a B2B fintech receives a Slack DM from a product manager: "Customer says our AI assistant gave a weird answer to a refund question. Here's the conversation ID. Can you check what happened?" The product manager is unbothered — these tickets come in, the platform team investigates, life moves on. The platform engineer expects a 20-minute investigation. It takes two and a half hours.

The architecture being investigated is genuinely complex, and that's the point. The user's question hits a Vue frontend, which calls a Node.js BFF, which calls a Python orchestrator microservice, which calls APIM (which holds the AI policies — content safety, token limits, routing), which calls Azure OpenAI. The orchestrator also calls a Java retrieval service for RAG context, which calls Elasticsearch, which calls a fine-tuned re-ranker model deployed to AKS. Eight services, three languages, two model providers (AOAI and the self-hosted re-ranker), one user-visible response that the customer is calling "weird." The platform engineer's first move is correct: pull the conversation ID and find the trace.

The trace is fragmented across two backends. Application traces from the Node BFF, Python orchestrator, Java retrieval service, and Elasticsearch are all in the company's Datadog instance — that's where the SRE team already operates, where the existing dashboards live, where the on-call alerts fire. APIM's traces and AOAI request/response telemetry are in Application Insights — because that's where APIM emits Application Insights traces by default, and the team has accepted that AI observability lives there. The W3C trace context propagates correctly within each backend but does not stitch automatically across them. To follow the request end-to-end, the engineer pulls the Datadog trace, copies the trace ID, then opens Application Insights and runs a KQL query keyed on that trace ID to find the corresponding APIM-side spans. The KQL is the kind that takes practice to write right: querying requests joined to dependencies, filtered by the operation_Id, with the LLM request/response bodies expanded from the generative-AI-gateway log chunks (which split at 32 KB with sequence numbers — the engineer hits this once and learns to reconstruct the message in KQL).

The diagnosis lands eventually. The retrieval service returned an unusually short context (2 of 5 expected documents) because two Elasticsearch shards had elevated latency that morning and the BFF's RAG-context call timed out. The orchestrator passed the truncated context to AOAI through APIM, which produced a confidently-worded answer based on incomplete grounding. The fix is two things: a longer timeout on the RAG-context call, and a Groundedness Detection guardrail at the APIM output (which would have caught the hallucination on the truncated context — see Blog 7). But the architectural lesson the engineer takes away from the postmortem is the trace-stitching cost. Two backends meant two queries, two query languages, two correlation hops. The 20-minute investigation became a 150-minute investigation because the AI portion of the trace lived in a different observability surface from the rest of the stack.

The architectural memo the team writes after the incident proposes what this blog is about: AI observability should flow into the same distributed-tracing stack as the rest of the company's services, not into a parallel Azure-side surface, because cross-stack debugging is the dominant operational cost. That isn't an argument against Azure Monitor — it's an excellent product for organizations whose entire stack lives there. It's an argument for AI observability being OTel-first by default, so it lands wherever the SRE team already operates.

  • TrueFoundry observability is OTel-first. OpenTelemetry exporters are the primary mechanism; metrics, logs, and traces flow as OTLP to whatever collector the customer points the gateway at. Native integrations with Datadog, Honeycomb, Tempo, Grafana Cloud, and any OTLP-compatible backend.   • Microsoft documents real performance and limit constraints honestly. The 32 KB log entry limit, 8,192-byte body limit, 2 MB message cap, and self-hosted-gateway best-effort delivery ("we don't guarantee all telemetry is pushed to Azure Application Insights") all shape production design.

§1 — Why trace stitching is the architectural question

Observability checklists find feature parity easily. Traces, logs, metrics. Sampling controls. Custom dimensions. End-to-end correlation. Both products check every box. The checklist comparison is correct but stops at the gateway boundary, and the gateway boundary is precisely where the operationally consequential question begins. The question is not whether each product produces good telemetry; it is whether the telemetry from the AI hop joins the same trace as the rest of the request lifecycle — and that depends on which backend it flows into.

For a single-service workload, this question doesn't matter. The AI service is the entire stack; one observability backend is fine. For a real distributed system — frontend, BFF, orchestrator, RAG retrieval, AI gateway, model providers, database, cache, message queues — the AI hop is one of many spans that have to compose into one trace if the on-call engineer is going to debug the incident in under an hour. The composition happens through W3C trace context propagation: every service forwards the traceparent header (and optionally tracestate) to its downstream calls; every span in every service includes the same trace ID; the observability backend stitches them together when it sees them.

This works cleanly when all the spans land in one backend. It works less cleanly when spans land in two backends — the trace ID is preserved, but the engineer has to query two systems, learn two query languages, and correlate manually. Most enterprises end up in this state when the AI gateway emits to Application Insights while the rest of the stack emits to Datadog or Honeycomb or self-hosted OTel infrastructure, and the operational cost of the split shows up not at platform-design time but at incident time, repeatedly, on every distributed-AI debugging session.

The three observability primitives

Walking the primitives explicitly:

  1. Traces — the request-flow story. A trace is a tree of spans showing how a request flowed through the system, with timing, status, and metadata at each span. For AI workloads, the LLM request span (with prompt, completion tokens, latency, model used) is often the most expensive and slowest span in the trace; it's also where most "weird answer" investigations land. The trace's value depends on whether all spans land in one backend.
  2. Metrics — the aggregate story. Per-second request rates, error rates, p50/p95/p99 latencies, token throughput, cost per minute. Metrics are how dashboards and alerts work. Both products produce equivalent metrics; the question is the dimensional richness (covered in Blog 6) and the destination of the metrics stream.
  3. Logs — the event story. Resource logs, audit logs, AI gateway logs, application logs. For AI workloads, the LLM request and response messages are first-class log events that often need to be captured (subject to redaction; subject to size limits). Both products produce equivalent log content; the question is where the logs flow and what the throughput cost is.

The architectural question for AI workloads specifically

For AI workloads, two observability concerns are sharper than they are for general API traffic:

  • LLM message capture. Production AI systems often need to capture full request/response messages (the prompt, the completion) for compliance, debugging, and quality evaluation. Both products support this; both have documented size limits. APIM's generative-AI-gateway logs split messages above 32 KB into chunks with sequence numbers (with a 2 MB hard cap per message); TrueFoundry's OTel export is bounded by the OTLP payload limits of the customer's collector configuration. The size handling matters because long-context AI workloads regularly exceed 32 KB on single messages.
  • Throughput cost of full-fidelity logging. Microsoft's own documentation states this directly: "enabling the logging feature caused a 40%-50% reduction in throughput when request rate exceeded 1,000 requests per second." This is not a defect; it is the documented cost of detailed Application Insights instrumentation. Production designs use sampling — typically 10-25% in high-traffic production, 100% during incidents. TrueFoundry's OTel export has its own throughput cost that depends on the collector's batching configuration. Neither is free.
The honest boundary on this argument

Azure Monitor is among the best-engineered observability platforms in the cloud-vendor space. Application Insights' end-to-end transaction view, Log Analytics' KQL query language, the AI-specific dashboard templates, the Managed Grafana integration, the deep AI observability for AOAI traffic — all genuinely best-in-class for the workloads they target. The architectural argument is not that Azure Monitor is poorly designed; it is that it is designed for organizations whose observability practice already lives in Azure. For those organizations, AI workloads inherit a mature, deeply-integrated surface. For organizations whose SRE stack lives elsewhere, the fit reverses — and the trace-stitching cost is what makes the architectural choice operationally consequential.

The rest of the blog walks both architectures in working detail. §2 walks the Azure observability surface — Application Insights for traces and request telemetry, Log Analytics for resource logs and KQL, generative-AI-gateway logs as a first-class category, the documented limits and constraints, and the Managed Grafana integration — with a working diagnostic-settings configuration and a representative KQL query. §3 walks TrueFoundry's OpenTelemetry-first surface — OTLP export with native exporters to multiple backends, W3C trace context propagation, the customer-stack integration shapes — with a working OTel collector configuration and the equivalent trace query. §4 walks three observability scenarios side-by-side. §5 ends with the editorial verdict.

Microsoft§2 — Azure: Application Insights, Log Analytics, generative-AI-gateway logs

Azure Monitor for APIM is a composition of Azure-native services. The architectural picture has three layers: Application Insights for end-to-end transaction tracing and request telemetry, Log Analytics as the unified log store with KQL as the query language, and Azure Monitor metrics for time-series aggregates with native dashboarding. Managed Grafana sits on top as the visualization surface for teams that prefer Grafana to Azure dashboards. AI-specific: generative-AI-gateway logs are a first-class log category that captures LLM request/response telemetry. The integration is mature; the constraints are documented; the throughput cost is non-trivial at scale.

Layer 1 — Application Insights as the trace surface

Application Insights is the request-tracing story. Every API request through APIM produces an Application Insights requests entry (the gateway-side span) and one or more dependencies entries (each backend call APIM forwards). Trace context propagation through W3C traceparent headers means application services upstream and downstream can stitch their spans into the same trace ID — provided they land in the same Application Insights instance.

The diagnostic settings exposed by APIM at the API or all-APIs level give precise control over what gets logged:

  • sampling.percentage — what fraction of requests get logged. 100 in development; 10–25 in high-traffic production per Microsoft's own guidance.
  • alwaysLog: "allErrors" — guarantees that error responses bypass sampling and are always logged. The standard production pattern: sample success at 10%, log all errors.
  • frontend.request.body.bytes / frontend.response.body.bytes — how many bytes of the request/response body to capture. Default is 0 (no body). Setting to 512 captures the first 512 bytes; setting to 8192 captures up to the per-body cap.
  • backend.request.body.bytes / backend.response.body.bytes — same controls for the backend leg of the call.
  • verbosity — the level applied to traces emitted by trace policies (verbose, information, error).

Layer 2 — Generative-AI-gateway logs as a first-class category

For LLM workloads specifically, APIM emits a separate log category: generative AI gateway logs. These capture LLM request and response messages — the actual prompt and completion text — subject to documented size handling:

"Generative AI gateway logs — LLM request or response messages up to 32 KB in size, if collected, are sent in a single entry. Messages larger than 32 KB are split and logged in 32 KB chunks with sequence numbers for later reconstruction. Request messages and response messages can't exceed 2 MB each."

The chunking behavior is operationally important. A long-context AI workload — RAG with 50 KB of retrieved documents in the prompt, for example — will produce a multi-chunk log entry. Reconstruction in KQL requires joining the chunks by their sequence numbers; the engineer who hits this once writes a reusable KQL function for next time. This is honest engineering — the chunking is the right answer to the size constraint — but it's a piece of operational nuance that production teams need to know about.

Layer 3 — The throughput cost

The most consequential constraint for production design is the documented throughput cost. From the Application Insights integration tutorial:

"Based on internal load tests, enabling the logging feature caused a 40%-50% reduction in throughput when request rate exceeded 1,000 requests per second. Application Insights is designed to assess application performances using statistical analysis. It's not: Intended to be an audit system. Suited for logging each individual request for high-volume APIs."

This is an unusually candid documentation entry. Microsoft is saying directly: Application Insights is designed for statistical observability, not for full-fidelity audit trails. Production systems hitting 1000+ RPS pay a real performance cost for 100% sampling. The mitigation is sampling — and Microsoft's own guidance ("100% for development, 10-25% for high-traffic production") encodes this. For audit trails specifically, the recommendation is to use Resource Logs (sent to Log Analytics or Storage Account directly) rather than Application Insights.

Layer 4 — Resource logs and Log Analytics

For audit-trail-grade logging that doesn't pay the Application Insights performance cost, Resource Logs are the right channel. Configured through Diagnostic Settings on the APIM resource, they emit two relevant categories:

  • ApiManagement Gateway — request/response logs from the gateway (separate from Application Insights' requests table).
  • Generative AI gateway logs — the LLM-specific category, including the chunked LLM messages described above.

Both flow into Log Analytics where they can be queried with KQL alongside other Azure resource logs. The resource-specific table mode (vs the legacy AzureDiagnostics catch-all) is the recommended setting; it gives properly typed columns rather than a single jsonified payload.

Layer 5 — Documented constraints that shape design

A handful of additional constraints that production teams need to design around:

  • 32 KB total log entry limit. If the combined size of all attributes in a gateway-log entry exceeds 32 KB, APIM trims the entry by removing all body and trace content. The size budget is across all fields, not per field.
  • 8,192-byte body limit per body in gateway logs. Bodies are capped at 8 KB even if the total entry has room. Long bodies are truncated.
  • Self-hosted gateway delivery is best-effort. Per Microsoft Learn: "we don't guarantee all telemetry is pushed to Azure Application Insights since it relies on Application Insights' in-memory buffering." For self-hosted-gateway deployments (Blog 3), audit-grade observability requires a different ingestion path.
  • Multiplexing requires Microsoft Support involvement. If you want to send telemetry to two different Application Insights instances from the same APIM service (the canonical use case: one for dev, one for prod with both enabled), this is supported but requires opening a support ticket. The default behavior is that the more granular logger overrides the broader one.
  • AMPLS (Azure Monitor Private Link Scope) ingestion caveats. If APIM is in a VNet linked to an AMPLS configured for Private-Only access mode, telemetry ingestion silently fails until the Application Insights and Log Analytics resources are added to the AMPLS. Documented operational gotcha.

What the operator writes — diagnostic settings + a representative KQL query

The Bicep below shows a working diagnostic configuration: 25% sampling on success traffic, 100% on errors, 512 bytes of frontend body capture, full LLM request/response message logging through the generative-AI-gateway log category. The companion KQL is what an on-call engineer writes to investigate a specific conversation, joining APIM gateway logs to LLM-message logs and reconstructing chunked messages:

Bicep
// Illustrative APIM diagnostic settings — production sampling pattern
resource apim 'Microsoft.ApiManagement/service@2024-05-01' existing = {
  name: 'contoso-apim'
}

// Application Insights logger
resource aiLogger 'Microsoft.ApiManagement/service/loggers@2024-05-01' = {
  parent: apim
  name: 'azuremonitor'
  properties: {
    loggerType: 'applicationInsights'
    credentials: {
      connectionString: appInsights.properties.ConnectionString
    }
  }
}

// Diagnostic at the all-APIs level — 25% sampling, always-log errors
resource appInsightsDiag 'Microsoft.ApiManagement/service/diagnostics@2024-05-01' = {
  parent: apim
  name: 'applicationinsights'
  properties: {
    alwaysLog: 'allErrors'             // bypasses sampling for any 4xx/5xx
    loggerId: aiLogger.id
    sampling: {
      samplingType: 'fixed'
      percentage: 25                   // production guidance: 10-25%
    }
    frontend: {
      request:  { headers: ['Content-type'], body: { bytes: 512 } }
      response: { headers: ['Content-type'], body: { bytes: 512 } }
    }
    backend: {
      request:  { headers: [], body: { bytes: 0 } }
      response: { headers: [], body: { bytes: 0 } }
    }
    verbosity: 'information'
  }
}

// Resource-log diagnostic setting — sends gateway + generative-AI-gateway
// logs to Log Analytics for audit-grade retention (no sampling cost there)
resource resourceLogs 'Microsoft.Insights/diagnosticSettings@2021-05-01-preview' = {
  scope: apim
  name: 'apim-to-loganalytics'
  properties: {
    workspaceId: logAnalyticsWorkspace.id
    logs: [
      { category: 'GatewayLogs', enabled: true }
      { category: 'GenerativeAIGatewayLogs', enabled: true }   // LLM messages
      { category: 'WebSocketConnectionLogs', enabled: false }
    ]
    metrics: [
      { category: 'AllMetrics', enabled: true }
    ]
  }
}
Composition based on Microsoft Learn for the diagnostic-logs reference, the App Insights integration tutorial, and Monitor Azure API Management. The pattern shown is the standard production configuration: sampled Application Insights for end-to-end traces, full-fidelity Resource Logs in Log Analytics for audit-grade retention, the Generative AI Gateway category enabled for LLM-message capture.

The companion KQL — what the on-call engineer writes when a "weird answer" ticket arrives. This query stitches APIM gateway logs to the generative-AI-gateway logs by request ID and reconstructs any chunked LLM messages:

KQL
// Reconstruct an LLM conversation for a specific request ID
// Joins gateway logs + generative-AI-gateway logs + handles chunking
let targetRequestId = "abc-123-456";
let gatewayLog = ApiManagementGatewayLogs
  | where TimeGenerated > ago(2h)
  | where CorrelationId == targetRequestId
  | project TimeGenerated, ApiId, OperationId, ResponseCode, TotalTime,
            BackendResponseCode, BackendTime, RequestSize, ResponseSize;
let llmLog = ApiManagementGatewayLlmLogs
  | where TimeGenerated > ago(2h)
  | where CorrelationId == targetRequestId
  // Reconstruct chunked messages — chunks have SequenceNumber and total ChunkCount
  | summarize
      RequestText  = strcat_array(make_list_with_nulls(RequestMessage),  ""),
      ResponseText = strcat_array(make_list_with_nulls(ResponseMessage), ""),
      TotalTokens  = sum(TotalTokens),
      PromptTokens = sum(PromptTokens),
      CompletionTokens = sum(CompletionTokens)
    by CorrelationId, ModelName;
gatewayLog
  | join kind=inner llmLog on $left.CorrelationId == $right.CorrelationId
  | project TimeGenerated, ApiId, OperationId, ModelName,
            RequestText, ResponseText,
            PromptTokens, CompletionTokens, TotalTokens,
            ResponseCode, TotalTime
Illustrative KQL pattern for reconstructing chunked LLM messages (per Microsoft's documented chunking behavior at the 32 KB threshold) and joining them to the gateway log entry by correlation ID. The query is the kind of thing an on-call engineer writes once and saves as a reusable function. Note: column names follow the documented schema for the resource-specific table mode.

What APIM is genuinely strong at — and the operating cost

What Azure Monitor for APIM does well is real and worth naming:

  • End-to-end transaction view in Application Insights. When other services in the same trace emit to the same App Insights, the transaction view is exceptional — you see every span, every dependency, every exception in one tree. For Azure-anchored stacks where everything lands in App Insights, this is best-in-class.
  • KQL is a powerful query language. For complex correlations, joins, time-series operations, and ad-hoc investigations, KQL outclasses most query languages in observability platforms. The chunked-message reconstruction shown above is the kind of operation KQL handles cleanly.
  • The Azure Monitor-based AI dashboard templates are mature. Microsoft ships pre-built dashboards covering token usage, model latency, error rates, content-safety blocks — useful out-of-the-box for teams that want a starting point.
  • Generative AI gateway logs are first-class. The dedicated log category for LLM messages, with documented chunking and size handling, is the right design — separating AI-specific telemetry from general gateway logs.
  • Documented constraints, honestly. The 40-50% throughput reduction at >1000 RPS, the 32 KB total / 8 KB body / 2 MB cap limits, the self-hosted-gateway best-effort delivery, the AMPLS ingestion caveat — all explicitly documented. Production teams designing around them can operate them reliably.
The honest caveats

(1) Cross-stack trace stitching. When other services in the request path don't emit to the same Application Insights instance — typical for organizations operating Datadog or Honeycomb as their primary distributed-trace backend — the engineer has to query two systems and manually correlate by trace ID. The 150-minute investigation in the opening scenario is this cost showing up. (2) The throughput-vs-fidelity trade-off. Production traffic above 1000 RPS pays a real performance cost for full-fidelity Application Insights logging. The recommended mitigation (sampling) is the right answer, but it means the trace data is statistical, not exhaustive. For workloads that need audit-grade trails, Resource Logs in Log Analytics are the right channel; teams operate two log streams. (3) The Azure-native default. The integration is excellent within Azure Monitor; integration to non-Azure observability backends (Datadog, Honeycomb, OpenTelemetry collectors) requires shipping logs out of Log Analytics through a separate forwarder or accepting the dual-backend trace-stitching cost.

TrueFoundry§3 — TrueFoundry: OpenTelemetry-first with native exporters

TrueFoundry's observability surface is shaped by a deliberate architectural choice: the gateway emits OpenTelemetry telemetry as its primary observability mechanism, and customers point that OTel stream at whatever collector they already operate. There is no proprietary observability backend the customer is steered toward; the SRE team's existing Datadog, Honeycomb, Grafana Cloud, Tempo, or self-hosted OTel collector is the destination. The architectural fact this produces is that AI observability lands in the same backend as the rest of the company's distributed-trace data — and the trace-stitching cost from the opening scenario disappears.

Layer 1 — OTel as the primary mechanism

The three OpenTelemetry primitives — Traces, Metrics, Logs — are first-class outputs of the gateway:

  • Traces. Every request through the gateway produces an OTel span representing the gateway's processing — admission, identity verification, rate-limit check, cache lookup, routing decision, backend call, response handling, guardrail checks. The span carries W3C trace context inherited from the incoming request, so the span stitches into the caller's trace automatically. Sub-spans capture the individual steps for engineers debugging policy decisions.
  • Metrics. Token throughput, request rates, error rates, latency percentiles, cache hit rates, guardrail block rates — emitted as OTel metrics with the metadata-driven dimensions described in Blog 6. The dimensional ceiling is wherever the customer's downstream metrics backend imposes one (Prometheus, Datadog, etc.) rather than a platform-imposed cap.
  • Logs. Gateway events — policy decisions, errors, audit events, guardrail outcomes — emitted as OTel logs with trace-context correlation. LLM request and response messages are first-class log payloads, subject to whatever size limits the customer's log backend imposes (no 32 KB chunking constraint at the gateway layer, though the customer's backend may have its own).

Layer 2 — Native exporters to multiple backends

The OTel-first design makes exporter integration the natural extension point. The customer points the gateway's exporter at any of:

  • Datadog via the OTel Collector's Datadog exporter or the native Datadog OTLP endpoint.
  • Honeycomb via OTLP/HTTP to the Honeycomb collector.
  • Grafana Cloud via OTLP to Grafana's hosted backend (Tempo for traces, Mimir for metrics, Loki for logs).
  • Self-hosted Tempo / Mimir / Loki via OTLP to the collector running in the customer's cluster.
  • New Relic, Elastic, Splunk Observability, Lightstep — any platform with OTLP ingestion.
  • Azure Monitor via the OpenTelemetry Distro for Azure Monitor — meaning the customer can choose Azure Monitor as the destination if they want to, but it's a configuration choice rather than the default architectural assumption.

The architectural implication is operational: AI observability inherits whatever observability practice the SRE team already has. If the team operates Datadog, AI traces appear in the same Datadog dashboards as the rest of the stack; the on-call engineer who pulls a trace in Datadog sees the AI hop alongside the BFF, orchestrator, RAG retrieval, and database calls — one query, one tool, one mental model.

Layer 3 — Trace context propagation and sampling

OpenTelemetry's W3C-standard trace context propagation is the mechanism that makes cross-stack stitching work. The gateway:

  • Reads the incoming traceparent from the request and uses its trace-id as the parent of the gateway span.
  • Forwards the traceparent to the LLM backend so backend-side telemetry (when the backend supports it) can stitch into the same trace.
  • Honors sampling decisions from the upstream traceparent sampling flag — if the caller's trace is sampled, the gateway span is sampled; if not, it isn't. This means the customer's overall sampling rate (typically 1-5% in high-traffic production) flows naturally through the AI hop without separate configuration.

The sampling-control axis is owned by the customer's OTel pipeline — typical patterns include head-based sampling at the source service, tail-based sampling at the OTel collector (intelligent sampling that keeps all error traces and a percentage of success traces), and adaptive sampling based on traffic levels. The gateway participates in whatever sampling regime the customer's pipeline implements; it doesn't impose its own.

Layer 4 — Customer-stack integration shapes

The integration shape varies based on the customer's backend, but the canonical patterns are:

  • Datadog-anchored stack: gateway emits OTLP to a Datadog Agent or directly to Datadog's OTLP endpoint. AI traces appear in APM alongside other services; LLM-message logs appear in Log Management; token-usage metrics appear in Metrics Explorer. One unified Datadog operational surface.
  • Honeycomb-anchored stack: gateway emits OTLP to Honeycomb's collector. Honeycomb's BubbleUp and high-cardinality query model is particularly well-suited to debugging AI workloads with rich metadata dimensions (per Blog 6's metadata-driven attribution).
  • Grafana Cloud or self-hosted Grafana stack: gateway emits OTLP to a collector that fans out to Tempo (traces), Mimir (metrics), Loki (logs). Customer operates the standard LGTM stack; AI observability is one more service in it.
  • Customer collector + multiple backends: gateway emits to a single OTel Collector deployed in the customer's cluster; the collector fans out to multiple backends (e.g., traces to Tempo for retention, metrics to Prometheus for alerting, logs to Datadog for searching). The fan-out logic is in the collector, not in the gateway — the gateway's responsibility is one OTLP stream.

The TrueFoundry observability topology diagram

TrueFoundry observability topology — gateway emits OTLP to a customer-operated OpenTelemetry collector that routes telemetry to whatever observability backend(s) the SRE team already operates. The architectural property is that AI observability lands in the same backend as the rest of the company's distributed-trace data.

What the operator writes — OTel collector configuration

The YAML below shows a working OTel collector configuration that receives OTLP from the TrueFoundry gateway and fans out to two backends — Datadog for APM and Loki for log retention. The companion gateway configuration shows how to point the gateway at the collector:

YAML
# Illustrative OTel Collector configuration deployed in customer cluster
# Receives OTLP from TrueFoundry gateway, fans out to Datadog + Loki
receivers:
  otlp:
    protocols:
      grpc: { endpoint: 0.0.0.0:4317 }
      http: { endpoint: 0.0.0.0:4318 }

processors:
  # Tail-based sampling: keep all errors + 10% of success traces
  tail_sampling:
    decision_wait: 10s
    policies:
      - { name: errors, type: status_code, status_code: { status_codes: [ERROR] } }
      - { name: high-latency, type: latency, latency: { threshold_ms: 5000 } }
      - { name: probabilistic, type: probabilistic, probabilistic: { sampling_percentage: 10 } }

  # PII redaction before export — applies regex-based substitution to message bodies
  attributes/redact:
    actions:
      - { key: llm.prompt, action: update, value: "[REDACTED-AT-COLLECTOR]" }
      - { key: llm.completion, action: update, value: "[REDACTED-AT-COLLECTOR]" }

  batch:
    timeout: 1s
    send_batch_size: 1024

exporters:
  # Datadog for APM (traces) + metrics
  datadog:
    api: { site: datadoghq.com, key: ${DD_API_KEY} }

  # Loki for log retention
  loki:
    endpoint: https://logs.contoso.internal/loki/api/v1/push

service:
  pipelines:
    traces:
      receivers:  [otlp]
      processors: [tail_sampling, attributes/redact, batch]
      exporters:  [datadog]
    metrics:
      receivers:  [otlp]
      processors: [batch]
      exporters:  [datadog]
    logs:
      receivers:  [otlp]
      processors: [attributes/redact, batch]
      exporters:  [loki]
---
# TrueFoundry gateway configuration — OTel export pointed at the collector
type: gateway-config
observability:
  otel_export:
    endpoint: http://otel-collector.observability.svc.cluster.local:4317
    protocol: grpc
    resource_attributes:
      service.name: truefoundry-ai-gateway
      service.namespace: ai-platform
      deployment.environment: prod
  trace_propagation:
    format: w3c               # honors incoming traceparent
  sampling:
    mode: parent_based        # follows upstream sampling decision
Composition consistent with TrueFoundry observability docs and the OpenTelemetry Collector configuration. The tail-based sampling policy is the canonical "keep all errors + 10% of success" production pattern that costs less than blanket sampling while preserving full debugging fidelity for incidents. The PII redaction processor is one example of customer-controlled telemetry shaping at the collector layer.
What this earns operationally

(1) Cross-stack trace stitching is automatic. The 150-minute investigation in the opening scenario becomes a 20-minute investigation when the AI hop emits to the same backend as the rest of the stack. The on-call engineer pulls a conversation ID, finds the trace, sees the AI span alongside every other span — one query, one tool. (2) Customer owns the pipeline. Sampling rate, retention policy, redaction rules, fan-out logic — all customer policies, not platform-imposed. The team that already operates an OTel pipeline applies the same rules to AI telemetry as everything else. (3) One ingestion path. No separate "AI observability" surface for the team to learn; AI traces appear in whatever distributed-trace tool the team already has muscle memory for. (4) OTel-first survives backend changes. If the org migrates from Datadog to Honeycomb (or to a self-hosted stack), the gateway configuration changes by one line — the destination URL. The gateway code is unchanged because OTLP is the wire format. (5) Vendor-agnostic by construction. No assumption that the customer is on Azure, on a particular cloud, or using a particular observability vendor. The integration shape is "OTLP to wherever you already have a collector."

§4 — Three observability scenarios compared

The three scenarios below walk concrete operational moments where observability architecture decides the response time. Each is shown side by side under both products.

SCENARIO 1"Weird answer" investigation across 8 microservices

The opening scenario closes here. A customer reports an incorrect AI response. The on-call engineer needs to trace the request through Vue → Node BFF → Python orchestrator → APIM → AOAI → Java retrieval → Elasticsearch → re-ranker.

Azure path

If all eight services emit to the same Application Insights instance (Azure-anchored stack), the trace stitches automatically into one end-to-end transaction view. The KQL query for the chunked LLM messages shown in §2 retrieves the full conversation. Investigation time: ~20 minutes for an experienced KQL user. If, however, the application services emit to Datadog (the typical case for a non-Azure-anchored stack), the engineer queries two systems and manually correlates by trace ID. Investigation time: 100-150 minutes — the case from the opening scenario. The architecture works well when the institutional choice is Azure Monitor end-to-end; less well when AI sits in a different backend than the rest.

TrueFoundry path

OTel-first emit to the same backend the SRE team already operates. The trace stitches across all eight services automatically because they share trace context and emit to the same collector / backend. The on-call engineer pulls the trace in their primary observability tool — Datadog APM, Honeycomb, Tempo — and sees the AI span alongside every other span. Investigation time: ~20 minutes regardless of which observability backend the org runs. The architecture's primary value: cross-stack trace stitching is automatic without requiring the AI hop to be in a specific vendor's observability surface.

SCENARIO 2High-traffic production at 2,500 RPS — full-fidelity vs sampled telemetry

A customer-facing AI feature is running at 2,500 RPS in peak hours. The platform team needs decisions on what telemetry to keep at full fidelity versus what to sample. Compliance requires full LLM message audit trails; engineering needs traces for debugging.

Azure path

Microsoft's documented 40-50% throughput reduction at >1000 RPS makes 100% Application Insights sampling impractical at 2,500 RPS. The institutional pattern: Application Insights at 10-25% sampling for traces (with alwaysLog: "allErrors" for full error capture); Resource Logs to Log Analytics for full-fidelity audit (the Generative AI Gateway category captures every LLM message, with the documented chunking for messages above 32 KB). Two log streams, both queryable through KQL, but the engineer has to know which one to query for which question. Effective; the throughput-vs-fidelity trade-off is documented and operable, with the cost being two parallel log pipelines.

TrueFoundry path

OTel collector tail-based sampling keeps all error traces and a configurable percentage of success traces (typically 5-10% at this scale), which preserves full debugging fidelity for incidents while reducing the volume the backend ingests. Logs export full LLM messages to whatever log retention backend the customer operates (Loki, Splunk, Datadog Logs); the message-size limit is whatever the customer's backend imposes rather than a platform-imposed 32 KB chunking constraint. Equivalent outcome with one OTel pipeline rather than two parallel log streams. The customer's collector config carries the throughput-vs-fidelity policy.

SCENARIO 3Migrating observability backend — Datadog to self-hosted Grafana Cloud

A platform team is migrating their observability stack from Datadog (current) to self-hosted Grafana Cloud (target) for cost reasons. The migration plan covers all 40 production microservices over Q3. The platform team needs to know what changes are required for the AI observability portion.

Azure path

If the existing AI stack emits to Application Insights, migrating to Grafana Cloud requires a parallel ingestion path: configure Application Insights to also forward telemetry to an OTel collector that routes to Grafana Cloud. This is achievable through Azure Monitor's diagnostic settings → Event Hub → OTel Collector pattern, but it's a non-trivial pipeline the team builds and operates. Alternative: change APIM diagnostic settings to point at a custom logger backed by Application Insights' OpenTelemetry Distro for Azure Monitor, then export OTLP from there. Both work; both are migration-specific engineering work. Workable but the Azure-Monitor-anchored architecture imposes migration cost specifically because that anchor exists.

TrueFoundry path

The gateway already emits OTLP to a customer-operated collector. The migration is a configuration change in the collector — change the exporter from Datadog to Grafana Cloud. Gateway configuration is unchanged. The OTLP wire format is stable across destinations. Direct fit; the OTel-first architecture is structurally migration-friendly because the destination is a configuration choice rather than an architectural assumption.

§5 — Editorial verdict

Best fit
Azure
Azure Monitor is one of the most mature, deeply integrated observability platforms in the cloud-vendor space. Application Insights' end-to-end transaction view is exceptional. Log Analytics' KQL outclasses most query languages for complex correlations. The Azure Monitor-based AI dashboard templates are battle-tested. The generative AI gateway log category with documented chunking and size handling is the right design for LLM-message capture. Microsoft's documentation is unusually candid about the constraints — the 40-50% throughput reduction at >1000 RPS, the 32 KB / 8 KB / 2 MB limits, the self-hosted gateway best-effort delivery, the AMPLS gotcha — all explicit. For organizations whose entire stack runs on Azure end-to-end and whose SRE practice is built around Azure Monitor, this is best-in-class.
Choose Azure if: Azure Monitor is the institutional observability surface for the rest of the stack, KQL is the team's query muscle, the existing Application Insights estate operates AI workloads alongside everything else, the AI-specific Azure-Monitor-based dashboard templates are operationally valuable, or the workload runs at low-enough RPS that the documented throughput cost of full-fidelity logging is acceptable.
Best fit
TrueFoundry
OpenTelemetry-first emit with vendor-agnostic OTLP export means AI observability lands wherever the SRE team already operates — Datadog, Honeycomb, Grafana Cloud, self-hosted Tempo, or any combination through OTel collector fan-out. The architectural property is that the AI hop joins the same trace as the rest of the company's distributed-trace data without requiring the rest of the stack to migrate to a particular vendor's observability surface. For distributed AI systems with 5-15 microservices in the request path, the cross-stack trace stitching this enables is decisive for incident-response time. The "weird answer" investigation from the opening scenario becomes the 20-minute case rather than the 150-minute case. For organizations evolving their observability stack — migrating between vendors, fanning out to multiple backends, applying customer-controlled redaction policies at the collector layer — the architecture is structurally migration-friendly.
Choose TrueFoundry if: the SRE team already operates Datadog, Honeycomb, Grafana Cloud, or self-hosted OpenTelemetry infrastructure; cross-stack trace stitching is decisive for incident-response time; backend portability is part of the org's observability strategy; or the customer-controlled OTel pipeline (sampling, redaction, fan-out) is the natural shape for the team's observability practice.

The most honest framing is that the two architectures encode different assumptions about where the customer's observability practice lives. Azure Monitor for APIM is engineered for organizations whose stack runs on Azure end-to-end — the integration is deep, the AI-specific dashboards are mature, the KQL fluency built across other Azure workloads carries over directly. TrueFoundry's OTel-first design is engineered for organizations whose SRE practice runs on a vendor-agnostic distributed-tracing backend — Datadog, Honeycomb, Grafana, or anything that consumes OTLP. Both architectures are coherent within their assumption.

The trace-stitching cost from the opening scenario is the operational metric that tests both. For Azure-anchored stacks, both architectures produce automatic stitching (TrueFoundry through OTel-to-Azure-Monitor via the OpenTelemetry Distro for Azure Monitor; APIM natively). For non-Azure-anchored stacks — which is most enterprises with mature SRE practices — TrueFoundry's OTel-first design produces automatic stitching while APIM produces a two-backend split that costs ~80-130 minutes per cross-stack debugging session. The cost compounds across the lifetime of the AI program where these debugging sessions are routine.

For most teams the right answer is shaped by the rest of the stack. If observability is Azure Monitor across the board, APIM's mature integration is the right call — the institutional muscle of KQL, the AI dashboard templates, the deep Foundry integration are all real value. If observability lives in Datadog or Honeycomb or Grafana or self-hosted Tempo (which is the typical case for organizations operating multi-cloud or with established SRE practices), the OTel-first architecture is the structural fit because trace-stitching is what determines incident-response time and trace-stitching across two backends is the dominant operational cost.
