What this blog argues

Both products now integrate with Model Context Protocol — Foundry Agent Service announced MCP support in preview at Build 2025, and TrueFoundry has had MCP server governance as a first-class platform primitive since 2024. The integration-availability comparison is a tie. The architectural question that decides operational fit is one level deeper: how does the platform govern MCP tool calls at the boundary between the agent and the MCP server, and what does the runtime model look like for organizations operating tens or hundreds of MCP servers across teams? Two structural differences shape the answer. (1) Azure's MCP integration is agent-centric — agents reference MCP servers as tool definitions, with allowed_tools and require_approval as the per-agent governance primitives, and Foundry Toolboxes as the multi-tool bundling mechanism. The runtime model centers on the agent as the unit of governance. (2) TrueFoundry's MCP governance is gateway-centric — MCP servers are workspace-scoped registry entries, the gateway sits in the call path between agent and MCP server, and the four-hook guardrail engine (Blog 7) applies pre-tool and post-tool inspection as platform primitives. The runtime model centers on the gateway as the unit of governance. Both architectures are coherent; both produce working MCP-enabled agentic systems; the operational properties of each differ in ways that matter for organizations operating MCP at scale.

§0 — TL;DR & Quick-Picks

An MCP server compromise that becomes a governance question

A financial-services firm in Singapore operates a portfolio of 40+ internal AI agents across product teams — customer-onboarding agents, KYC research agents, regulatory-filing agents, internal-IT agents. Each agent has access to a subset of 18 MCP servers the platform team operates: an internal customer-data MCP server, a market-data MCP server, several SaaS integrations (Confluence, Jira, GitHub, ServiceNow), an Azure DevOps MCP, and a few specialized ones the data team built. The architecture works well operationally — agent teams onboard quickly, they pull MCP servers from the platform's catalog, the platform team handles MCP server uptime and versioning.

On a Wednesday morning, the firm's security team forwards an alert. One of the third-party SaaS integrations the team uses — a relatively obscure project-management tool's MCP server — has had a security incident upstream. The vendor disclosed that an attacker may have compromised credentials capable of issuing MCP responses with crafted payloads. The vendor's recommendation: pause all MCP traffic to their server until they complete remediation, expected to take 18-36 hours. The platform team needs to make this happen across 40 agents that may be using the affected MCP server, and they need to do it in minutes, not hours.

The platform team's investigation maps the dependency graph. Of the 40 agents, 11 currently include the affected MCP server in their allowed_tools configuration. Some include it actively; some included it during early development and haven't removed it. The platform team's central registry of which agents reference which MCP servers is an out-of-band spreadsheet maintained when registrations happen, not a runtime-queried platform fact. Verifying which agents are actually calling the MCP server in the past 24 hours requires querying observability data across all agent runs, joining to the agent registry, and producing a dependency report. The investigation takes 90 minutes. The actual remediation — updating the MCP server's allow-list config or revoking the credential — is in some sense the easy part once the dependency graph is established.

The remediation procedure runs to completion three hours after the security alert arrived. The team's incident postmortem captures three architectural lessons. First, per-agent allow-list configuration produces a dependency graph that lives in the agents — knowing which agents reference an MCP server requires querying the agent definitions, not querying the MCP server's consumer registry. Second, governance configured per-agent doesn't compose into platform-wide policy — there's no single place to say "no agent in this firm can use that MCP server right now." Third, real-time inspection of MCP calls (parameter validation, response inspection) is not a first-class capability of the agent-runtime layer — the platform team would have liked to put a temporary inspection rule in front of all calls to the affected MCP server while diagnosis continued, but the agent-centric model makes this an out-of-band operation. The team's followup architecture work: build a custom MCP gateway in front of all MCP servers, route all agent-to-MCP traffic through it, implement centralized allow-listing and inspection at the gateway. The remediation works but the platform team has built — at meaningful engineering cost — what their agent-runtime should arguably provide as a primitive. The architectural lesson the team takes from the incident is one this blog is about: at MCP scale, governance has to be at the boundary between agent and MCP server, not inside each agent's configuration.

Agent-centric vs gateway-centric
For organizations operating 5-10 MCP servers and 5-10 agents, both architectures work fine. Per-agent configuration scales by N×M (agents × servers); gateway-policy governance scales by M (just the servers).

§1 — Why MCP governance is a boundary problem

Model Context Protocol's architectural design has converged the industry on a clean separation: agents speak MCP; tools are exposed by MCP servers; the protocol handles discovery, invocation, and response. The convergence is genuinely valuable — Microsoft, Anthropic, Google, and most of the agent-platform vendor space have converged on MCP as the integration standard, which means tools written once can be consumed by any compliant agent runtime. The architectural question MCP doesn't answer is what platform sits at the boundary between agent and MCP server, and how that boundary is governed.

The boundary matters because MCP servers are by design third-party (or third-team) capabilities that an agent calls into. Even MCP servers operated by trusted internal teams are different trust domains from the agent — different deployment cadences, different on-call rotations, different security postures, different rate of change. A compromised MCP server, a misbehaving MCP server, or just an MCP server that needs temporary access restrictions during incident response is a normal operational pattern, not an exotic edge case. The platform that handles MCP at scale needs governance at this boundary as a first-class capability.

Three governance questions the boundary must answer

  1. Allow-listing. Which MCP servers can a particular agent call? Which tools within those servers? The traditional answer is per-agent configuration — each agent's definition lists allowed servers and tools. This works at small scale; at large scale it produces a dependency graph that lives in N×M agent configurations rather than as a queryable platform fact.
  2. Real-time inspection. What happens to the parameters the LLM constructs for an MCP tool call before they reach the MCP server? What happens to the response from the MCP server before it's added to the agent's next-turn context? These are the questions Blog 7's four-hook model addresses; for MCP specifically, they are the Pre-Tool and Post-Tool hooks.
  3. Cross-cutting policies. How does the platform express "no agent in this org can call MCP server X right now" as a single policy change? How does it express "all calls to MCP server Y must be audit-logged"? How does it express "calls from production agents to MCP server Z require approval, calls from dev agents don't"? Per-agent configuration doesn't compose to these policies cleanly; gateway-policy governance does.

Why MCP at scale changes the architectural choice

The question of agent-centric vs gateway-centric governance is not architecturally interesting at small scale. A team with 3 agents and 4 MCP servers can operate either model effectively — the per-agent configuration is small enough to manage, and the policy expressiveness needed is minimal. The architectural choice gets interesting at the 20+ MCP servers × 50+ agents scale that organizations operating mature agentic AI programs reach. At that scale:

  • Per-agent allow-list maintenance becomes a coordination problem across many agent teams.
  • Cross-cutting MCP server policies (security incident response, compliance constraints) need to be expressible at one place.
  • The dependency graph between agents and MCP servers needs to be queryable in real time, not derivable from agent configurations.
  • Real-time inspection at the tool boundary becomes the natural place for centralized parameter validation, sensitive-data redaction, and tool-call audit logging.
The honest boundary on this argument

Foundry Agent Service's MCP integration is genuinely well-engineered. Foundry Toolboxes (preview) is a strong pattern for centralizing tool authentication and bundling — it explicitly addresses the "configure each tool separately on every agent" problem the per-agent model has at scale, and it does it in an MCP-native way (the toolbox itself is an MCP-compatible endpoint). The require_approval field is a sensible primitive for high-risk operations. The integration with Microsoft Entra for centrally-managed authentication is the right architectural choice. The argument is not that Azure's MCP integration is poorly designed; it is that the agent is the unit of governance in Foundry's runtime model, which produces different operational properties than gateway-centric governance at large MCP scale. Foundry Toolboxes mitigate this for tool bundling specifically; for cross-cutting MCP server policies, the difference remains structural.

Microsoft§2 — Azure: Foundry Agent Service + MCP tool + Toolboxes

Azure's MCP integration sits inside Foundry Agent Service — the managed agent runtime that handles agent definition, conversation threads, tool invocation, and persistent state. MCP is one tool type among several (the others include Code Interpreter, File Search, Azure AI Search, Bing grounding, OpenAPI tools, Agent-to-Agent connections, and Foundry Toolboxes). The integration has matured rapidly through 2025, with the preview announcement at Build 2025 followed by GA-track stabilization through late 2025 and early 2026.

Layer 1 — The MCP tool definition

The MCP tool is a structured object on an agent definition. From Microsoft's MCP documentation, the four canonical fields:

  • server_url — the URL of the remote MCP server (e.g., https://api.githubcopilot.com/mcp/ for GitHub's MCP server, or https://learn.microsoft.com/api/mcp for the Microsoft Learn MCP).
  • server_label — a unique identifier for this MCP server within the agent (used to disambiguate tool calls when multiple MCP servers are attached).
  • allowed_tools — optional allow-list of specific tools within the MCP server that this agent can use. If omitted, all tools the MCP server exposes are available.
  • require_approval — controls the approval workflow. Values include "always" (every tool call requires approval), "never" (no approval needed), or a specific tools list.

At runtime, the MCP tool is invoked as part of the agent's tool-use cycle: the LLM decides to call an MCP tool, the Agent Service runtime forwards the call to the MCP server (after applying the allowed_tools filter and the require_approval check), the MCP server executes and returns a response, the response is added to the conversation thread, and the agent continues. The runtime handles header injection (for authentication), thread storage, and the approval flow.

Layer 2 — Public vs private MCP server topology

The infrastructure shape of the MCP server determines which deployment options are available:

  • Public endpoints. Any publicly accessible remote MCP server works with both Basic and Standard agent setups. This includes SaaS MCP servers (Zapier, Linear, Notion, etc.), Microsoft-provided MCPs (Microsoft Learn MCP, Azure DevOps MCP), and any MCP server an organization exposes publicly.
  • Private endpoints. MCP servers not exposed to the public internet require Standard Agent Setup with private networking and a dedicated MCP subnet. The subnet must be delegated to Microsoft.App/environments (Azure Container Apps), which is the recommended deployment target for private MCP servers per Microsoft's documentation.

The architectural fact: private MCP servers are infrastructure-coupled to Azure Container Apps. The recommendation is operationally clean for organizations already running ACA; for organizations running their MCP servers on AKS, EKS, GKE, or other K8s, the recommended path requires either migrating those MCP servers to ACA or accepting the Network Secured Foundry caveat documented next.

The Network Secured Foundry caveat

Per Microsoft Learn: "When you use a Network Secured Microsoft Foundry, you can't use private MCP servers deployed in the same virtual network. You can only use publicly accessible MCP servers." This is a real and significant constraint for organizations with strong network-isolation requirements — a Network Secured Foundry deployment cannot consume MCP servers deployed inside the same VNet, only public MCP servers. The architectural workaround is to expose internal MCP servers via Azure Front Door or another public-facing fronting service, which adds the cost of an extra hop and a public attack surface for an internal capability. Microsoft documents this honestly; the constraint is the constraint.

Layer 3 — Foundry Toolboxes for multi-tool bundling

Foundry Toolboxes (preview as of early 2026) is Microsoft's answer to the "configure each tool separately on every agent" scaling problem. A Toolbox bundles multiple tools — Web Search, Code Interpreter, File Search, Azure AI Search, MCP servers, OpenAPI tools, Agent-to-Agent connections — into a single MCP-compatible endpoint. Agents point to the Toolbox endpoint as a single MCP server; the Toolbox handles discovery and routing to the underlying tools.

Operationally, this is genuinely valuable for organizations operating mature agent platforms: tool authentication is centralized at the Toolbox layer, agents authenticate to the Toolbox using Microsoft Entra (typically DefaultAzureCredential with the agent's identity or the project's managed identity), and individual tool credentials don't need to be passed by each agent. The Toolbox is itself MCP-compatible, so any MCP-capable runtime can consume it (not just Foundry's).

The architectural fact: Foundry Toolboxes turn N tool registrations into 1 toolbox registration per agent, which mitigates the per-agent allow-list scaling problem at the tool-config level. What it doesn't change is the agent-as-unit-of-governance model — each agent still references the Toolbox as a per-agent tool configuration, and cross-cutting policies still need to be expressed per-agent (or constructed externally on top of the Toolbox).

Layer 4 — Authentication options

Four authentication patterns are documented for MCP servers behind Agent Service:

  • Key-based authentication — function keys (x-functions-key) for Azure Functions-hosted MCP servers, or generic API keys for third-party MCP servers. Stored as project connections in Foundry, not embedded in agent code.
  • Microsoft Entra identities — agent identity or project managed identity (recommended for Microsoft-hosted services and internal MCP servers). Integrates with the Entra-backed identity model from Blog 2.
  • OAuth identity passthrough (OBO — On-Behalf-Of) — for MCP servers that need to act on behalf of the end user. The user's token is passed through to the MCP server, which then operates with the user's permissions. Used for SaaS integrations like Azure DevOps that have OAuth-scoped permissions.
  • Unauthenticated — supported for limited scenarios (typically dev/test) but explicitly not recommended for production. Microsoft documents this as a possible option while strongly steering away from it.

Layer 5 — Documented operational constraints

A handful of constraints production teams need to design around:

  • Non-streaming MCP tool call timeout: 50 seconds. If the MCP server takes longer than 50 seconds to respond, the call fails. This is a real constraint for MCP servers that perform complex operations — databases queries, large-document processing, long-running computations. Microsoft's recommendation is to ensure MCP servers respond within this limit; for genuinely long-running operations, the streaming pattern (which has different timeout semantics) is the alternative.
  • Microsoft's untested-server caveat. The documentation explicitly states: "Microsoft doesn't test or verify these servers. Microsoft has no responsibility to you or others in relation to your use of any non-Microsoft services." This is honest; it's also the operational fact that makes governance at the boundary essential.
  • Azure API Center registration is optional. Teams that want a private organizational tool catalog can register MCP servers in API Center, which provides a discovery surface within the Foundry portal. Without API Center registration, MCP servers are configured per-agent without centralized cataloging.

What the operator writes — Foundry Agent with MCP tool

The Python below shows a working Foundry Agent definition with an MCP tool referencing the Microsoft Learn MCP server, plus a Foundry Toolbox bundling multiple internal tools, with allow-listing and approval workflow. The pattern follows Microsoft's documented quickstart:

Python
# Illustrative Foundry Agent with MCP tool + Toolbox + approval workflow
from azure.ai.agents.models import MessageTextContent, McpTool, ToolboxTool
from azure.ai.projects import AIProjectClient
from azure.identity import DefaultAzureCredential

project_client = AIProjectClient(
    endpoint=PROJECT_ENDPOINT,
    credential=DefaultAzureCredential(),
)

# MCP tool — Microsoft Learn MCP for documentation grounding
ms_learn_mcp = McpTool(
    server_label="microsoft_learn",
    server_url="https://learn.microsoft.com/api/mcp",
    allowed_tools=["microsoft_docs_search"],   # restricted allow-list
)

# MCP tool — internal customer-data MCP server (private, ACA-hosted)
customer_data_mcp = McpTool(
    server_label="customer_data",
    server_url="https://customer-data-mcp.internal.contoso.com/mcp",
    allowed_tools=["lookup_customer", "list_accounts"],   # explicit allow-list
)

# Foundry Toolbox — bundle of internal capabilities exposed as one MCP endpoint
internal_toolbox = ToolboxTool(
    server_label="contoso_internal",
    project_connection_id="conn_internal_toolbox",
    # Toolbox handles centrally-managed Entra auth, credential injection,
    # token refresh, and policy enforcement at runtime
)

# Create the agent with the MCP tools + toolbox attached
with project_client:
    agent = project_client.agents.create_agent(
        model="gpt-4o-mini",
        name="kyc-research-agent",
        instructions=(
            "You research customer information for KYC compliance. "
            "Use Microsoft Learn for product documentation. "
            "Use customer_data tools for internal lookups. "
            "Always cite the source of any factual claim."
        ),
        tools=ms_learn_mcp.definitions
              + customer_data_mcp.definitions
              + internal_toolbox.definitions,
    )

# Create thread + run with require_approval for sensitive operations
thread = project_client.agents.threads.create()
project_client.agents.messages.create(
    thread_id=thread.id,
    role="user",
    content="Look up customer 12345 and summarize their account history.",
)

# Resource configuration: require approval for write operations
mcp_resources = customer_data_mcp.resources
mcp_resources.set_approval_mode("always")  # require approval for every tool call

run = project_client.agents.runs.create(
    thread_id=thread.id,
    agent_id=agent.id,
    tool_resources=mcp_resources,
)
# ... approval handling loop, run polling, response retrieval ...
Composition based on Microsoft Learn for the MCP integration in Foundry Agent Service and Foundry Toolboxes. The agent has three tool configurations — two direct MCP servers and one Toolbox bundle. The allowed_tools lists provide per-server tool allow-listing; set_approval_mode("always") requires approval for every customer-data tool call (recommended for the high-risk write operations that customer-data MCP exposes).

What Azure is genuinely strong at — and the agent-centric caveat

What Foundry Agent Service's MCP integration does well is real:

  • The MCP integration is mature and well-documented. The MCP tool definition with server_label, server_url, allowed_tools, and require_approval is the right shape. The integration with Microsoft Entra for centrally-managed authentication aligns with the institutional identity model.
  • Foundry Toolboxes is a strong pattern. Bundling multiple tools into a single MCP-compatible endpoint with centralized authentication is the right architectural move for organizations that want to reduce per-agent tool configuration overhead. The fact that the Toolbox itself is MCP-compatible means it composes with MCP-capable runtimes beyond Foundry.
  • The approval workflow is thoughtful. The require_approval field with "always", "never", or specific tools list is the right primitive for high-risk operations. Combined with logging of approvals and tool calls, it's a sensible governance pattern at the agent level.
  • Microsoft is honest about the trust boundary. The explicit caveat that Microsoft doesn't test third-party MCP servers is honest engineering communication. The recommendation to use trusted servers, allow-list tools, require approval for writes, and review data shared with MCP servers is sound guidance.
  • Azure DevOps MCP / Microsoft Learn MCP / and other Microsoft-provided MCP servers integrate cleanly through Foundry Toolboxes' organizational catalog. For organizations using Microsoft tooling extensively, this is real time-savings.
The honest caveats

(1) Cross-cutting MCP server policies are agent-distributed. "Pause MCP server X across all agents" requires updating allowed_tools on every agent that references X — the operation depends on the per-agent dependency graph, which lives in the agent definitions rather than as a queryable platform fact. (2) Real-time inspection at the tool boundary is not a first-class capability of the Agent Service runtime. Parameter validation, sensitive-data redaction in tool responses, and tool-call audit at the boundary require external middleware or are limited to the require_approval pause-and-review flow. (3) The Network Secured Foundry caveat excludes private MCP servers in the same VNet, forcing teams with strong network-isolation requirements to expose internal MCP capabilities publicly. (4) The 50-second non-streaming timeout bounds what MCP servers can do synchronously. (5) Foundry Toolboxes mitigate the per-agent tool count problem, but each agent still references the Toolbox per-agent — the agent-as-unit-of-governance shape remains.

TrueFoundry§3 — TrueFoundry: gateway-centric MCP with Pre-Tool / Post-Tool hooks

TrueFoundry's MCP runtime model places the gateway in the call path between the agent and the MCP server. Every agent-to-MCP call traverses the gateway; the four-hook guardrail engine from Blog 7 applies MCP Pre-Tool (parameter validation before tool execution) and MCP Post-Tool (response inspection before next-turn context) as platform primitives at the boundary. MCP servers are workspace-scoped registry entries; the agent's MCP access is governed at the workspace and gateway-policy level, not in the agent's own configuration. The architectural fact this produces: cross-cutting MCP server policies live in one place, and the dependency graph between agents and MCP servers is a queryable platform fact rather than a property of N×M agent configurations.

Layer 1 — MCP servers as workspace-scoped registry entries

The MCP overview describes the model: an MCP server is a registered platform object in a workspace (the same workspace boundary that bounds identity, FinOps, and observability per Blogs 2, 6, 8). The registration captures: the server's URL, authentication credentials (managed as platform secrets, not embedded in agent code), the allowed-tools list at the workspace level, the rate-limit policies, and the guardrail bindings.

The architectural implication: agents in a workspace inherit access to whatever MCP servers the workspace registers. There's no per-agent allow-listing in the agent's own definition; the agent has access to the workspace's registered MCP servers (subject to gateway-policy filtering). Adding a new agent to a workspace is faster (no per-agent MCP configuration); pausing an MCP server across all agents is faster (one workspace-level config change).

Layer 2 — The four-hook guardrail engine applied to MCP boundaries

The four hooks from Blog 7 — LLM Input, LLM Output, MCP Pre-Tool, MCP Post-Tool — apply at the appropriate boundaries. For MCP traffic specifically, two hooks matter most:

  • MCP Pre-Tool hook — inspects the tool invocation the LLM has constructed before the gateway forwards it to the MCP server. Guardrails attached here see: tool name, parameters, calling agent identity, calling user (when OAuth identity passthrough is in use), and surrounding context. Common policies: parameter validation (employee_id must match calling user's reporting chain), tool allow-listing per role, sensitive-value detection, rate-limit-per-tool enforcement.
  • MCP Post-Tool hook — inspects the tool's response before the gateway returns it into the LLM's next-turn context. Guardrails attached here see: full tool response, response structure, tool name, and calling identity. Common policies: PII redaction, secret detection (prevent API keys from round-tripping), internal-identifier redaction, response-content auditing.

The hooks are platform primitives, not application-side code. The team configures them once at the workspace or virtual-model level; every agent in scope inherits the inspection. New agents inherit the policies automatically; updates to the policies apply to all agents in scope without per-agent updates.

Layer 3 — Identity propagation and FinOps inheritance

The workspace boundary that bounds MCP server access is the same boundary that bounds identity, FinOps, and observability. This is operationally meaningful:

  • Identity propagation. Calls from agents in workspace-research to MCP servers carry the workspace's identity context. OIDC / Entra integration from Blog 2 means the gateway can pass through user identity for OAuth scenarios, or use the workspace's service identity for system-level calls. The agent doesn't manage credentials; the platform does.
  • FinOps attribution. MCP tool calls are accounted to the calling workspace's budget, with the metadata-driven attribution from Blog 6. A team operating multiple agents in a workspace gets the aggregate MCP cost as a single attribution dimension; cross-workspace MCP cost is the sum across workspaces.
  • Observability uniformity. MCP tool calls emit OTel telemetry through the same pipeline as other gateway calls (Blog 8). Trace context propagates from the agent through the MCP call and back; the trace stitches into the customer's existing observability backend.

Layer 4 — Cross-cutting policies as one operation

The architectural payoff of the gateway-centric model is the cross-cutting policy operation. The opening scenario's "pause MCP server X across all agents" is a single workspace-level config change: update the MCP server's registration to set state: paused (or similar), the change propagates through NATS config sync to all gateway pods within seconds, and every subsequent call to that MCP server fails closed (or routes to an audit-only path) until the registration is re-enabled.

Other cross-cutting patterns the gateway-centric model handles cleanly:

  • Rate-limit per MCP server across all consuming agents — the gateway enforces a single rate limit at the boundary regardless of how many agents are calling.
  • Per-MCP-server audit logging — every call to a sensitive MCP server is logged with full request/response, regardless of which agent initiated it.
  • Schema validation — the gateway can validate that tool calls match expected MCP server schemas, catching misconfigured agents before requests reach the server.
  • Sensitive-data filtering — PII redaction, secret detection, and similar policies apply uniformly to all calls to a given MCP server through the Mutate-mode hooks.

The TrueFoundry MCP runtime topology diagram

TrueFoundry MCP runtime topology — workspace-scoped MCP registry; gateway in the call path with Pre-Tool and Post-Tool hooks; cross-cutting policies live at the gateway-policy layer; identity, FinOps, and observability inherit from the same workspace boundary used elsewhere in the platform.

What the operator writes — workspace MCP registration with hooks

The YAML below shows a working configuration: a workspace with three MCP server registrations (one paused after a security alert), Pre-Tool and Post-Tool hooks applied with parameter validation, PII redaction, and audit logging:

YAML
# Illustrative workspace-scoped MCP server registry
type: workspace-mcp-config
workspace: research
servers:
  # MCP server 1 — internal customer data (high-sensitivity)
  - name: customer-data-mcp
    url: https://customer-data-mcp.internal.contoso.com/mcp
    state: enabled
    auth:
      type: managed_identity     # workspace's service identity
      target: customer-data-api.contoso.com
    rate_limit:
      requests_per_minute: 1000  # workspace-wide; enforced at gateway
    allowed_tools: [lookup_customer, list_accounts, get_account_history]

  # MCP server 2 — market data (medium-sensitivity)
  - name: market-data-mcp
    url: https://market-data.contoso.internal/mcp
    state: enabled
    auth: { type: managed_identity, target: market-data.contoso.internal }
    rate_limit: { requests_per_minute: 5000 }
    allowed_tools: ["*"]         # all tools allowed

  # MCP server 3 — third-party PM tool (PAUSED after security incident)
  - name: third-party-pm-mcp
    url: https://saas-pm.example.com/mcp
    state: paused                # blocks all calls platform-wide
    state_reason: "Security incident upstream; vendor remediation in progress"
    state_changed_at: 2026-04-30T08:14:00Z

---
# Hooks applied at the MCP boundary — workspace-scoped policy
type: mcp-guardrails
workspace: research
hooks:
  # Pre-Tool — parameter validation BEFORE the MCP server sees the call
  - hook: mcp_pre_tool
    mode: validate           # parallel; cancel-on-fail
    strategy: enforce
    applies_to:
      - server: customer-data-mcp
        tool: lookup_customer
    checks:
      - type: parameter_validation
        rules:
          - param: customer_id
            rule: must_match_pattern: "^CUST-[0-9]{8}$"
          - param: customer_id
            rule: must_be_in_business_unit_of: ${request.user.business_unit}

      - type: tool_allowlist_per_role
        rules:
          - role: kyc_analyst
            allowed: [lookup_customer, list_accounts]
          - role: relationship_manager
            allowed: [lookup_customer, list_accounts, get_account_history]

  # Post-Tool — response inspection and redaction BEFORE next-turn context
  - hook: mcp_post_tool
    mode: mutate             # sequential; layered modifications
    strategy: enforce
    applies_to:
      - server: customer-data-mcp
    checks:
      - type: pii_redaction
        priority: 1
        fields_to_redact: [ssn, full_dob, phone, email]
      - type: secret_detection
        priority: 2
        action: block        # block any response containing apparent secrets

  # Audit logging — applies to all calls to high-sensitivity MCP servers
  - hook: mcp_pre_tool
    mode: validate
    strategy: audit          # observe-only; never blocks
    applies_to:
      - server: customer-data-mcp
    checks:
      - type: audit_log
        log_request: full
        log_response: redacted
Composition consistent with TrueFoundry's MCP overview docs and the four-hook guardrail model from Blog 7. The pattern shown is what the financial-services scenario from §0 needs: a single state: paused change pauses the third-party MCP across all consuming agents instantly. Pre-Tool parameter validation prevents customer_id manipulation; Post-Tool PII redaction prevents sensitive fields from round-tripping into next-turn context. Audit logging applies uniformly to all sensitive-MCP traffic.
What this earns operationally

(1) The opening scenario's incident-response time becomes minutes, not hours. The "pause MCP server X across all agents" operation is a single workspace config change with ~3-second propagation through NATS config sync. The 90-minute investigation to map the dependency graph becomes unnecessary; the 18 affected agents are simply all agents in the workspaces that registered the MCP server, queryable in real time. (2) Cross-cutting MCP policies compose cleanly. Adding a new policy ("audit-log every call to MCP server X") affects all consuming agents at once; new agents inherit the policies automatically. (3) Real-time inspection at the tool boundary is a platform primitive. Pre-Tool parameter validation, Post-Tool response inspection, and audit logging apply at the gateway-policy layer rather than requiring application-side middleware. (4) One boundary, four concerns. Workspace bounds identity (Blog 2), FinOps (Blog 6), observability (Blog 8), and MCP server access — same boundary, same RBAC, same operational model. Teams don't learn a new boundary concept for MCP. (5) The dependency graph is queryable. "Which agents call MCP server X?" is "agents in workspaces that register X" — a platform fact, not a derivation from N×M agent configurations.

§4 — Three MCP-runtime scenarios compared

The three scenarios below walk concrete moments where MCP runtime architecture decides the operational outcome. Each is shown side by side under both products.

SCENARIO 1Emergency MCP server pause across 40+ agents during security incident

The opening scenario closes here. A third-party SaaS MCP server has had a security incident; the platform team needs to pause all agent-to-MCP traffic to that server within minutes while diagnosis continues.

Azure path

The team queries observability data + agent definitions to find the 11 of 40 agents that reference the MCP server in allowed_tools. Updates each agent definition to remove the affected server from the allow-list — 11 agent updates. For agents using Foundry Toolboxes that include the server, updates the Toolbox config. Each agent update is a configuration deploy through the agent management API; the propagation is bounded by Foundry's agent-config update timing. Total elapsed including dependency mapping: ~90-180 minutes. Workable but operationally heavy. The team's incident-response time on MCP issues is dominated by the dependency-graph mapping cost.

TrueFoundry path

One workspace-level config change: state: paused on the MCP server registration. NATS config sync propagates to all gateway pods in ~3 seconds. Every subsequent call to the MCP server fails closed (or routes through audit-only depending on policy choice). The dependency graph is implicit: agents in workspaces that registered the MCP server are the affected agents, queryable as a platform fact. Total elapsed: under 10 seconds for the pause; the dependency-mapping cost from the Azure path is essentially zero. Direct fit; the architecture's strongest scenario for incident response. Cross-cutting MCP server policies are a single platform operation rather than an N-agent coordinated change.

SCENARIO 2Multi-tool agent with bundled capabilities and approval workflow

A team is building a customer-support agent that needs access to: Microsoft Learn MCP for product docs, an internal knowledge-base MCP, code interpreter, file search over support tickets, and Azure DevOps MCP for creating tickets. Sensitive operations (creating tickets, escalating to engineering) require approval.

Azure path

✅ Foundry Toolboxes is exactly designed for this. The team configures a Toolbox bundling Web Search, Code Interpreter, File Search, Microsoft Learn MCP, internal-KB MCP, and Azure DevOps MCP into a single MCP-compatible endpoint. Centralized Entra authentication at the Toolbox layer. require_approval on Azure DevOps MCP for ticket creation. Microsoft DevOps MCP is a Microsoft-provided server with documented integration patterns. The agent points at the Toolbox; one tool reference covers all six capabilities. Best-in-class fit. Foundry Toolboxes is genuinely the right architectural pattern for multi-tool bundling within Azure.

TrueFoundry path

Same architectural shape, different mechanism. The team registers the six MCP servers (or HTTP capabilities) in the workspace; the agent, by virtue of workspace membership, has access to all six. Pre-Tool hooks enforce per-role allow-listing if needed. Approval workflow is implemented through the same Pre-Tool hook with require_approval mode for Azure DevOps MCP write operations. The bundling happens at the workspace level rather than as an explicit Toolbox primitive — same operational outcome (one registration boundary covers all capabilities) achieved through workspace inheritance rather than explicit bundling. Equivalent outcome. The Toolboxes-as-MCP-endpoint primitive is a real Azure advantage for organizations that want explicit bundling; workspace-as-implicit-bundle is a real TrueFoundry advantage for organizations that want governance-by-membership.

SCENARIO 3Network-isolated deployment with private MCP servers

A healthcare provider operates AI workloads behind strong network isolation. All compute runs in a private VNet (Azure) or VPC (AWS); data-residency rules require that internal MCP servers (patient-data MCP, billing MCP, EHR MCP) cannot be exposed to the public internet. The agent platform must consume these private MCP servers without forcing them to be public-facing.

Azure path

The team deploys MCP servers to Azure Container Apps with internal-only ingress on a dedicated MCP subnet delegated to Microsoft.App/environments. Standard Agent Setup with private networking is required. If the Foundry deployment uses Network Secured Foundry (the strongest network-isolation posture), the documented caveat applies: "you can't use private MCP servers deployed in the same virtual network. You can only use publicly accessible MCP servers" — which forces the team to choose between Network Secured Foundry's network posture and consuming private MCP servers, or to expose internal MCP servers via Front Door (adding a public attack surface for internal capabilities). Workable for non-Network-Secured deployments; constrained for Network Secured Foundry. The infrastructure-coupling to ACA forces a deployment choice for internal MCP servers.

TrueFoundry path

MCP servers deploy to whatever K8s cluster is appropriate — same deployment shape as any other workload (Blog 9). The gateway runs in the same private network; trusts internal MCP server endpoints over private DNS or service-mesh; no public exposure required. Network isolation is the default; private MCP servers are first-class. The same state: paused pattern from Scenario 1 applies; the same Pre-Tool / Post-Tool hooks apply. Direct fit; the K8s-native architecture handles network-isolated MCP deployment without special configuration. For organizations with strong network-isolation requirements, this is structurally simpler than the Azure Container Apps path with the Network Secured Foundry caveat.

§5 — Editorial verdict

Best fit
Azure
Foundry Agent Service's MCP integration is well-engineered for its design intent. The MCP tool definition with server_label, server_url, allowed_tools, and require_approval is the right shape for per-agent governance. Foundry Toolboxes (preview) is a strong architectural pattern for multi-tool bundling — exposing multiple capabilities as a single MCP-compatible endpoint with centrally-managed Entra authentication mitigates the per-agent tool count problem within the agent-centric model. The integration with Microsoft-provided MCP servers (Azure DevOps MCP, Microsoft Learn MCP) is genuinely valuable for Microsoft-tooling-heavy organizations. The honest documentation about the trust boundary, the 50-second timeout, the Network Secured caveat, and the untested-server caveat is clear and operationally useful. For organizations operating moderate MCP scale with the agent-as-unit-of-governance model, this is best-in-class.
Choose Azure if: the agent-as-unit-of-governance model fits the team's structure, Foundry Toolboxes' multi-tool bundling with centrally-managed Entra authentication is operationally valuable, the Microsoft-provided MCP servers (Azure DevOps, Microsoft Learn) are mission-critical, the Foundry Agent Service runtime is the institutional choice for agent operations, or the MCP scale is moderate enough that per-agent allow-list maintenance is operationally tractable.
Best fit
TrueFoundry
The gateway-centric MCP runtime with the four-hook guardrail engine produces a different operating model. MCP servers are workspace-scoped registry entries; cross-cutting policies are single platform operations; the dependency graph between agents and MCP servers is a queryable platform fact rather than a property of N×M agent configurations. Pre-Tool and Post-Tool hooks apply real-time inspection at the boundary as platform primitives — parameter validation, sensitive-data redaction, audit logging are configured once at the workspace level and apply uniformly. The same workspace boundary that bounds identity (Blog 2), FinOps (Blog 6), and observability (Blog 8) also bounds MCP server access, so teams operate one boundary concept across all four concerns. For organizations operating MCP at scale (20+ servers across many teams), the architectural value is real: incident-response time on MCP issues drops from hours to minutes; cross-cutting policies are one operation rather than N coordinated changes; real-time inspection is a primitive rather than custom middleware.
Choose TrueFoundry if: MCP traffic needs gateway-policy inspection at the tool boundary, MCP server governance needs to be platform-wide rather than per-agent, the four-hook guardrail engine's Pre-Tool and Post-Tool hooks are decisive for security/compliance posture, network-isolated deployments with private MCP servers are required without the Network Secured Foundry caveat, or the operational simplicity of one workspace boundary across identity, FinOps, observability, and MCP is institutionally valuable.

The most honest framing is that the two architectures encode different unit-of-governance assumptions. Azure's Foundry Agent Service treats the agent as the unit — agents reference MCP servers via per-agent tool configurations, governance primitives like allowed_tools and require_approval live on the agent, and Foundry Toolboxes bundle tools at the configuration layer to mitigate per-agent scaling problems. TrueFoundry treats the workspace and the gateway as the units — MCP servers are registered platform objects, agents inherit access via workspace membership, and gateway-policy hooks apply real-time inspection. Both architectures are coherent within their assumption.

The MCP-scale dimension is what makes the choice operationally consequential. At 5-10 agents and 5-10 MCP servers, both architectures work fine and the differences are theoretical. At 20-50 agents and 15-30 MCP servers (which is the scale enterprise agentic AI programs are reaching as of early 2026), the architectural differences become operational realities — incident response time, cross-cutting policy expressiveness, and dependency-graph queryability all show up as concrete operational metrics. For organizations approaching that scale, the gateway-centric model's properties are real value.

The Microsoft-provided MCP servers (Azure DevOps MCP, Microsoft Learn MCP, and others Microsoft is rolling out) are a genuine Foundry advantage. Microsoft is investing in first-party MCP server quality for the tooling its customers care about; teams operating heavily on Microsoft's stack get those integrations as part of the institutional package. The integration is excellent for Microsoft-tooling-heavy organizations. For organizations whose MCP server portfolio is dominated by internal-built or third-party servers, the integration advantage is smaller; for those organizations, the gateway-centric governance model is what determines fit.

For most teams the right answer is shaped by MCP scale and the existing platform institutional posture. Moderate-MCP-scale Azure-anchored organizations should use Foundry Agent Service with Toolboxes — the integration is mature, the Microsoft-provided MCPs are valuable, and the agent-centric model is operationally tractable at the scale. Large-MCP-scale organizations or organizations with strong network-isolation requirements should consider the gateway-centric model — the cross-cutting policy expressiveness and the real-time-inspection primitives are decisive at scale, and the K8s-native MCP deployment path avoids the Network Secured Foundry caveat.
